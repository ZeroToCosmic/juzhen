## A. 业务语义澄清（需业务方/客户确认）

### A1. 任务类型与现有系统的关系
- **问题**：任务类型 `publish/browse/comment/like/follow` 中，"发布"指什么？与现有内容发布（Buffer GraphQL）和 AdsPower 浏览器发布是什么关系？同一账号的任务来源（BCS 任务 vs 现有 Campaign）如何共存不冲突？
- **当前 PRD**：任务类型枚举列出，未定义与现有系统边界。
- **决策**：发布是否仅限 BCS 路径；现有 Campaign/策略执行在新系统中是否保留为"兼容模式"。
- **影响**：任务模型、账号占用冲突（同一账号两套系统同时执行）、数据迁移范围。

### A2. 账号部署的 AdsPower 指纹参数范围
- **问题**：导入 Excel 中的"可选 AdsPower 指纹参数"包含哪些字段？来源、校验规则、默认值？
- **当前 PRD**：仅提"指纹参数按导入配置写入"。
- **决策**：字段清单 + 必填性 + 版本兼容（AdsPower Local API 支持哪些）。
- **影响**：部署执行器（F26）实现、导入模板定义。

### A3. 多租户的真实形态
- **问题**：客户是外部 SaaS 多租户，还是内部多团队？租户间是否共享物理设备（Agent/Profile 归属一个租户还是可共享）？Profile 能跨租户吗？
- **当前 PRD**：全链路 tenant_id，但未定义设备/Profile 的租户归属规则。
- **决策**：设备归属租户；Profile 是否允许跨租户共享。
- **影响**：数据模型、分配器、NATS Subject ACL、验收 #9。

### A4. 容量上限 300 的依据
- **问题**：每机 max_accounts=300 是硬件估算、AdsPower 限制、还是经验值？超限行为（拒绝/排队/警告）？
- **当前 PRD**：默认 300，事务性防超卖。
- **决策**：数值依据 + 超限策略。
- **影响**：容量分配器、验收 #19。

### A5. 风控参数的业务输入
- **问题**：pacing（随机延时区间）、冷却时长（2h）、熔断阈值（3 次）、窗口并发（3）等默认值是否有业务/运营依据？是否要可调且按租户？
- **当前 PRD**：有默认值，配置版本化支持修改。
- **决策**：默认值来源 + 哪些允许租户自调。
- **影响**：F6 配置、F23 熔断、验收 #3。

### A6. "盖楼"依赖的具体业务规则
- **问题**：DAG 依赖的"多父"实际场景是否只有盖楼（楼主+引用）？父 Handle 的 VERIFIED 判定标准（comment_id 可见？时长窗口？）？
- **当前 PRD**：多父 AND + VERIFIED 门禁 + 等待上限。
- **决策**：父 Handle 判定细则 + 等待上限默认值（当前实现未配置）。
- **影响**：Handle 门禁、DLQ 行为、验收 #2。

## B. 架构矛盾点（需技术决策）

### B1. 消息骨干：NATS 还是 HTTP 拉取（最终裁决）
- **问题**：PRD 写 NATS JetStream 推送；当前参考实现是 Agent HTTP 拉取（pull-based）。**二选一或分阶段**（先拉取后推送？）。
- **当前 PRD**：NATS 为主干（M2 引入）。
- **决策**：v1 交付形态；若 NATS，明确接入点与迁移步骤；若拉取，修订 PRD 相关章节（F12/F17/验收 #10）。
- **影响**：Agent 架构、消息语义（at-least-once vs 轮询）、验收 #10。

### B2. 中控与 Web 的部署关系
- **问题**：中控独立进程（FastAPI 8000）+ Flask Web(5000) 双服务，还是合并？认证（JWT）放哪一层？
- **当前 PRD**：中控独立部署（v1 同机）。
- **决策**：进程拓扑 + 认证归属（central 自鉴权 vs Web 代理）。
- **影响**：部署、安全验收。

### B3. 现有系统数据边界
- **问题**：5 个现有 SQLite（accounts/execution_v2/comment_campaign/selector_probe/management）哪些迁入 central、哪些保留原样、哪些只读？迁移分批怎么定？
- **当前 PRD**：第 14 章分期迁移，未定具体批次。
- **决策**：迁移批次清单 + 每批的源/目标/幂等键/回滚。
- **影响**：F1 账号、策略迁移、验收 #0。

### B4. Agent 与现有单机模式并存
- **问题**：同一台 Windows 电脑上，现有 launcher 单机模式与 Agent 模式能同时跑吗？Profile 会不会被两套逻辑同时打开？
- **当前 PRD**：未定义。
- **决策**：并存策略（互斥/分时/禁止）。
- **影响**：Profile 排他锁范围、部署手册。

## C. 验收标准缺口（PRD §12 需补强）

### C1. 每条验收标准的可度量化
- **问题**：19 条验收多为"行为性"描述（如"成功率展示"），缺少**量化指标与判定方式**：目标值（成功率≥?、延迟≤?、并发=3）、数据来源（看板 API？日志？）、自动化 vs 人工。
- **当前 PRD**：§15.4 有压测断言（500 账号），但业务验收未量化。
- **决策**：为每条验收补"指标 + 阈值 + 验证方式（自动测试/接口断言/人工步骤）"。
- **影响**：验收可执行性（这是"验证路线"的根基）。

### C2. 性能基线
- **问题**：单任务 500+ 账号的端到端吞吐、任务创建 API 延迟（P99）、看板刷新延迟（≤1s 的测量方法）、Agent 心跳规模（100 设备）？
- **当前 PRD**：有定性要求。
- **决策**：性能指标表（指标/目标/测量工具/测试脚本）。
- **影响**：验收 #18、压测。

### C3. 安全验收
- **问题**：JWT 认证、租户 ACL、日志脱敏、凭据加密的验收方式？（自动测试覆盖哪些，人工渗透哪些？）
- **当前 PRD**：§15.5 契约性描述。
- **决策**：安全测试清单。
- **影响**：F7、安全章节。

### C4. 兼容性验收
- **问题**：AdsPower API 版本兼容、Windows 10/11、Python/Node 版本矩阵的验收步骤？
- **当前 PRD**：§8 提及。
- **决策**：版本矩阵 + 验收方式。

## F. 打磨后的 PRD v3 结构建议

```
1. 背景目标（不变）
2. 术语（增补）
3. 角色租户（增补设备/Profile 归属规则）
4. 业务流程（按 B1 裁决更新消息链）
5. 功能需求（每条标注：验收方式引用）
6. 状态机（不变 + 补 PUBLISHED_UNVERIFIED 流转细则）
7. 数据模型（补 D2 契约）
8. 非功能（补 C2 性能表）
9. 日志监控（补 D4 告警表）
10. 迭代规划（按里程碑 + 每里程碑验证路线：范围/交付物/自动测试/接口验证/人工验收）
11. 风险（不变）
12. 验收标准（补 C1 量化 + C3 安全 + C4 兼容）
13. 部署（按 B2 裁决）
14. 迁移（补 B3 批次清单）
15. 一致性安全（不变）
附录：错误码表(D1)、接口契约(D2)、保留策略(D3)、指标定义(C2)
```
