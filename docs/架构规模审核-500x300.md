# 架构规模审核报告：500 台 × 300 账号/台

**日期**：2026-08-11 | **对象**：PRD v2 架构 + 参考实现（tag `prototype-2026-08-11`）
**规模假设**：设备 500 台（持续扩增）；账号 500×300 = **150,000**；每台默认并发窗口 3 → 全系统峰值 **1,500 窗口**

---

## 1. 规模指标换算

| 指标 | 数值 | 依据 |
|---|---|---|
| 总账号数 | 150,000 | 500 × 300 |
| 活跃窗口（峰值） | 1,500 | 500 × 3（窗口并发上限） |
| 心跳 | ~17 次/秒 | 500 台 ÷ 30s 间隔 |
| Agent 拉取 | 50~100 次/秒 | 500 台 ÷ 5~10s 轮询 |
| 结果回传 | ~12.5 次/秒 | 1,500 窗口 ÷ 平均 2 分钟/任务 |
| 综合写速率 | 30~50 写/秒 | 心跳+结果+状态事件 |
| 结果表年增量 | ~1,800 万行/年 | 50,000 结果/天 × 365 |
| WS 连接 | 个位数 | 仅 Web 管理员，非设备 |

**核心洞察：活跃集很小（1,500 窗口），总量很大（150,000 账号）**——这决定架构的可行性与实现要点。

---

## 2. 逐层容量审核

### 2.1 中控数据层（数据库）

| 项 | 审核 |
|---|---|
| SQLite 起步（v1 决策） | ⚠️ **500 设备规模不成立**。SQLite 单写者：30~50 写/秒理论可行（极限 ~1000/s），但锁竞争下心跳/结果延迟不可控，且多实例（回收器+API+调度）无法共享。**结论：SQLite 起步仅适用于 ≤50 设备/单实例；500 规模必须 PG**（参考实现已支持 `CENTRAL_DB_URL` 切换） |
| 表规模 | ✅ 账号 15 万行、设备 500 行——索引（tenant_id, status）下无压力 |
| 活跃租约 | ✅ 最多 1,500 行（= 窗口数）——回收器只应扫活跃集（status 索引），**不得全表扫描** |
| 结果/审计增长 | ❌ **需要保留与归档策略**：task_results 年 1,800 万行，audit_events 更多——无策略则 2 年内库膨胀不可控（PRD D3 缺失项） |
| 多实例并发 | ⚠️ 分配器/回收器多实例必须 PG 的 `SELECT ... FOR UPDATE SKIP LOCKED` + 唯一约束（参考实现 F12a 已设计未实测） |

### 2.2 中控 API/调度（FastAPI）

| 项 | 审核 |
|---|---|
| 心跳/拉取吞吐 | ⚠️ 综合 70~150 请求/秒（心跳 17 + 拉取 100）。FastAPI 同步路由走线程池可扛，但**心跳 upsert 写需节流/批处理**（同一设备 30s 内重复心跳合并）；拉取间隔必须可配置（`AGENT_PULL_INTERVAL`） |
| 分配器（tick） | ❌ **当前实现不可扩展**：`dispatch_queued` 全量扫描 QUEUED 再排序——15 万账号排队时每 tick 全表扫描+排序。**必须改为：索引驱动取 TOP-N（优先级+等待）+ 事务性认领**（PG 行锁）；tick 频率由"队列深度"驱动而非固定轮询 |
| 定时调度（scheduled_tick） | ⚠️ PENDING 任务扫描同样需要 status 索引 + 分页；15 万账号的周期任务量需评估（若每账号每日一任务 → 每日 15 万触发，集中在时点 → 需削峰/错峰） |
| 回收器 | ✅ 只扫活跃租约（~1,500）——加 status 索引即可 |
| WebSocket 事件 | ✅ 事件量 ~20/s，Redis Stream MAXLEN 1000 窗口足够 |

### 2.3 消息通道（当前 HTTP 拉取）

| 项 | 审核 |
|---|---|
| 拉取式 | ✅ 500 台 × 5-10s 轮询 = 50-100 req/s——**可实现**；但拉取间隔决定任务下发延迟（5-10s）——业务可接受（分钟级任务）。**此规模下 NATS 推送的收益仍不显著**（100 req/s 远未到瓶颈），支持 B1 决策：v1 拉取、v2 NATS |
| 结果回传 | ✅ 12.5/s 直写 + Inbox 去重——无压力 |

### 2.4 Agent 侧（每台）

| 项 | 审核 |
|---|---|
| 单台 300 账号 / 3 窗口 | ✅ 300 是"容量水位"（部署上限），不是同时打开数；AdsPower 串行网关 ✓；每台本地 SQLite（execution_v2.db 等）+ WAL ✓ |
| 执行内核分发 | ⚠️ **500 台分发现有模块**需打包方案（PyInstaller + NSSM）——PRD F25 未实现，属交付项 |
| 本地数据 | ✅ 每台本地库独立，无跨机共享 |

### 2.5 网络/风控/多租户

| 项 | 审核 |
|---|---|
| 网络 | ✅ 流量极小（心跳+拉取小载荷）；跨公网需 TLS（PRD 已有） |
| 风控容量模型 | ❌ **缺失**：150,000 账号 × 冷却/最小间隔 = 有效并发模型未定义。需明确"每账号每日动作上限/最小间隔/冷却"→ 这决定实际吞吐（1,500 窗口可能被风控约束到远低于上限） |
| 多租户（M4） | ✅ 15 万账号分区后各租户规模更小；索引必须 tenant_id 前缀（模型已含） |

## 3. 审核结论

### ✅ 架构方向成立（无需推翻）
分层、状态机唯一权威、租约+Fencing、Outbox/Inbox、HTTP 拉取、Agent 复用现有内核——**在 500×300 规模下架构正确**。参考实现已验证核心机制。

### ⚠️ 必须升级的实现项（500 规模的前提条件）
1. **数据库**：PG（SQLite 起步仅限 ≤50 设备/开发）
2. **分配器**：全表扫描 → 索引驱动 TOP-N + 事务认领（PG SKIP LOCKED）
3. **心跳/拉取**：节流合并 + 拉取间隔可配置 + FastAPI 异步化（必要处）
4. **索引**：subtasks(status, priority)、tasks(status)、devices(tenant, heartbeat) 等
5. **保留/归档**：task_results/audit_events 分区+归档（否则 2 年失控）

### ❌ 需新增的定义（PRD 补齐项）
1. **容量模型**：每账号动作频率上限/最小间隔/冷却（决定真实吞吐）
2. **规模压测计划**：分阶段验证（见 §4）
3. **监控告警**：写延迟、tick 时延、队列深度、DB 增长

## 4. 规模验证路线（分阶段，可执行）

| 阶段 | 规模 | 环境 | 验证内容 | 指标 |
|---|---|---|---|---|
| S1 单机验证 | 1 台设备 / 10 账号 | SQLite + 本机 | 功能回归 + 执行链路 | 现有 132 测试 + 烟雾验收 |
| S2 中等规模 | 50 设备 / 15,000 账号 | PG + 单实例 | 心跳/拉取/分配/结果全链路（fake-agent 负载模拟器） | 心跳写延迟 <50ms；tick 时延 <500ms；无写排队 |
| S3 目标规模 | 500 设备 / 150,000 账号 | PG + 多实例 | 分配吞吐、回收器、事件通道、保留策略 | tick 时延 <1s；结果回传 P99 <2s；DB 增长可控 |
| S4 扩展性 | 1,000+ 设备 | 同上 | 水平扩展验证（API 多实例 + PG 连接池） | 线性扩展 |

**前置依赖**：fake-agent 负载模拟器（模拟 N 台设备的心跳/拉取/执行/回传）——这是规模验证的关键工具，列入开发里程碑。
