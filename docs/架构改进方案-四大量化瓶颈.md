# 四大量化瓶颈解决方案（1500 窗口 / 15 万账号规模）

**日期**：2026-08-11 | **前置**：`docs/架构规模审核-500x300.md`、`docs/架构改进方案.md`

---

## 问题 1：数据库写入雪崩与租约回收器卡死

### 1.1 问题分解（先纠正量级认知）

"每秒上千条 DB 写"是把**事件**误当作**DB 写**。正确的分级：

| 数据 | 真实频率（1500 窗口） | 是否落 DB |
|---|---|---|
| 动作级进度（滚动/点击/日志） | 每秒数百~上千 | ❌ 不落库（Agent 本地日志 + 可选旁路流） |
| 租约续期 | 25/s（60s 间隔） | ✅ 但需合并降频 |
| 结果回传 | 12.5/s | ✅ |
| 状态迁移 | ~5/s | ✅ |
| **实际 DB 写** | **~40/s** | 可控（PG 轻松承受） |

### 1.2 解决方案

**① 事件与状态分离（核心）**
- 动作级进度 → Agent 本地 JSONL 日志（现有 `record_browser_log` 模式），**不写 central DB**
- DB 只保存"状态机迁移 + 结果 + 租约"（低频里程碑）
- 需要实时进度时：Agent 经 WS 直推（不过 DB）或 Redis 缓冲

**② 续租降频 + 去索引刷写**
- 续租间隔 60s → **120~300s**（租约超时 5min 不变，安全余量足够）
- **续租不 bump revision**（参考实现缺陷：`renew_lease` 每次 `revision += 1` 触发索引更新——改为仅更新 `last_progress_at`，revision 只在状态迁移时 +1）
- 续租合并为批量 SQL（同设备多租约一次 UPDATE）

**③ 回收器只扫活跃集（独立 leases 表）**
- 独立 `leases` 表（活跃租约 ≤1,500 行）+ 部分索引 `WHERE expires_at IS NOT NULL`
- 回收分批（每轮 ≤100）+ 短事务（单租约一事务，避免长事务锁）
- 回收决策无需扫 subtasks 全表（数万~百万行）

**④ 心跳与写分离**
- 心跳写入独立轻量 `device_heartbeats` 追加表（INSERT 不 UPDATE）或 Redis 暂存 60s 回写；`devices` 主行的状态由聚合任务定期刷新
- PG `synchronous_commit=off`（心跳/日志类写可接受极少丢失，状态迁移保持 on）

**⑤ 索引维护**
- subtasks 状态索引用**部分索引**（WHERE status 活跃）——非活跃行不参与索引，UPDATE 活跃→终态时索引页减少
- 大结果表按月分区（写入只落当月分区）

### 1.3 验证
- S3 压测断言：DB 写速率 ≤50/s、写延迟 P99 <50ms、回收器单轮 <500ms、索引膨胀受控（表大小曲线）

## 问题 2：15 万账号任务拆解与 DAG 计算内存爆表

### 2.1 问题确认
一次性生成 15 万 subtasks + dependency_edges + 全量拓扑排序 → OOM/CPU 100%。

### 2.2 解决方案

**① 拆解异步化 + 分片（核心）**
- 任务创建接口：同步只做**校验 + 任务行落库**，返回 `task_id`（202）
- 拆解作为**后台 job**（走 Outbox/独立 worker）：按分片（每片 1,000~5,000 账号）流式生成
  - 每片：批量 INSERT（`executemany` 500/批）
  - 每片完成更新任务进度字段（`created_subtasks/total`）→ Web 端轮询进度
- 15 万账号拆解 = 30~150 片，单片内存占用恒定（O(片大小)）

**② DAG 检测降复杂度**
- **无依赖任务跳过检测**（绝大多数任务）——当前 `detect_cycle` 无条件跑，先短路
- 有依赖任务：按**连通分量**分组，只对分量内节点检测（盖楼 = 星型/链式小图，分量 ≤ 数千）；拒绝"全量互联"的畸形输入（依赖边总数上限校验，如 ≤ 账号数×10）
- 拓扑排序用流式 Kahn（生成片内即校验）

**③ 依赖写入分批**
- dependency_edges 同样按片写；子任务初始状态：有依赖 WAITING_DEPENDENCY / 无依赖 QUEUED（分片内判定）

**④ 配额前置校验**
- 任务创建前校验：账号数 > 上限（如 50 万）拒绝；依赖边数 > 上限拒绝——防畸形输入打垮中控

### 2.3 验证
- S3 专项：创建 15 万账号任务 → 拆解完成时间 <2min、峰值内存 <1GB、无 OOM；期间 API 无阻塞（拆解在后台 job）
- 单测：10 万节点无环图、环图拒绝、依赖上限拒绝

## 问题 3：WebSocket 实时事件风暴打垮前端

### 3.1 问题确认
每秒上千条事件推前端 → DOM 卡死/内存泄漏；慢客户端背压挤爆网关。

### 3.2 解决方案

**① 事件分层（前端只收里程碑）**
- **里程碑事件**（状态迁移/结果/任务创建）→ WS 推送（低频，~20/s）
- **动作级进度日志** → 不推 WS；前端按需通过 REST 分页拉取（`GET /logs`），或订阅独立"日志流"（可选、限流）
- central 转发前按类型过滤：无订阅者的事件类型不发布

**② 服务端聚合（事件合并器）**
- central 侧窗口聚合（500ms~1s）：同租户同类型事件合并计数（如 `subtask.result` 20 条/秒 → 合并为 `{type, count, last_status}` 1 条/秒）
- 看板计数类数据 → 只推增量计数，前端累加（避免全量重绘）

**③ 前端渲染节流（现有 bcs.js 需改）**
- DOM 更新用 `requestAnimationFrame`/定时器合并（500ms 批处理一次渲染）
- 看板/子任务统计改为**增量更新**（合并 diff 更新），不整表重绘（当前是全量 `loadDashboard`——改为事件驱动增量 + 30s 全量校准）
- 列表类（子任务明细）虚拟滚动或只显示摘要（详情点击加载）

**④ 背压与慢客户端（已有基础，补强）**
- 每连接缓冲上限（已有 2000 条）→ 超限断开 + 快照重连（已有）
- **发送队列水位检测**：队列 >50% → 自动降级该连接为 5s 轮询（断开 WS，前端切轮询）
- 网关级：WS 连接数上限 + 每连接消息速率上限（令牌桶），超限断开

**⑤ 订阅过滤协议**
- WS 连接参数支持 `?types=result,status`——前端只订阅需要的类型，central 按类型分发（减少 90% 流量）

### 3.3 验证
- S3 压测：1500 窗口并发事件下 central WS 出口速率 ≤50 条/s（聚合后）；前端内存稳定（30 分钟无泄漏，Chrome 内存曲线）；慢客户端降级生效（带宽限速模拟）

## 问题 4：端侧磁盘爆满与 AdsPower 响应迟钝

### 4.1 问题确认
300 Profile × 500MB-1GB 缓存 = 150-300GB；AdsPower 管理 300 环境 API 退化到数十秒；看门狗误强杀。

### 4.2 解决方案

**① 每台上限下调为实测值（最直接）**
- PRD 默认 300 是未经实测的假设 → **先 S2 实测单台容量**（磁盘占用/API 响应/稳定性），按结果定上限（预估 100~150）
- `max_accounts` 已是设备字段，按机器磁盘容量动态计算（`max_accounts = 可用磁盘GB × 系数`），Agent 心跳上报

**② 缓存治理（Agent 侧定时任务）**
- AdsPower 提供清理缓存能力（Local API 支持清理浏览器缓存）：Agent 每日低峰（如 04:00）批量清理
- 清理策略：仅清"超过阈值缓存大小"的 Profile（按 Profile 目录大小检测）；活跃窗口的 Profile 跳过
- 目标：单 Profile 缓存控制在 200MB 内 → 300 Profile = 60GB（可控）

**③ 磁盘水位监控**
- Agent 心跳上报 `disk_free_gb`；central 看板展示 + 告警（<50GB 警告，<20GB 停止新部署/新任务）
- 部署分配器（F26 容量）把磁盘纳入候选条件

**④ AdsPower 慢响应治理（防看门狗误杀）**
- **慢 ≠ 死**：升级阶梯的强杀判定改为"连续 N 次超时（N=3）且持续 >M 秒（M=60）"——单次 15s 超时仅重试，不触发强杀
- **动态背压**：Agent 监控 AdsPower API 响应时间（滑动窗口均值）；均值 >阈值（如 5s）→ 降低本机窗口并发（3→2→1），恢复后回升——从源头减少对 AdsPower 的压力
- 看门狗升级阶梯保留，但强杀前必须"标记 UNVERIFIED + 人工告警"（已有设计）——把误杀从"频繁"降为"罕见"

**⑤ 容量模型联动**
- 每台上限下调直接影响"300 账号/台"假设 → 500 台 × 100-150 账号 = 5-7.5 万账号容量；**扩机器比扩单台容量更符合现实**（PRD 目标 15 万账号需要 ~1,000-1,500 台或更高单台容量实测值）——**这是必须让业务方知晓的容量现实**，影响 PRD 目标与预算

### 4.3 验证
- S2 实测：单台 150 Profile 的磁盘占用/AdsPower API P95 响应/稳定性数据 → 定 max_accounts 系数
- 模拟：缓存膨胀到阈值 → 清理任务生效；API 变慢 → 动态背压降并发 → 看门狗不误杀（日志断言）

## 汇总：对参考实现的具体改动清单

| # | 改动 | 位置 |
|---|---|---|
| 1 | `renew_lease` 去掉 revision+1（续租不刷索引） | `central/leases.py` |
| 2 | 独立 `leases` 表 + 部分索引；回收器只扫活跃集、分批 | `central/models.py`、`central/leases.py` |
| 3 | 任务拆解异步化（job + 分片 + 进度字段） | `central/tasks.py`、新增拆解 worker |
| 4 | DAG 检测短路（无依赖跳过）+ 连通分量 + 依赖边上限 | `central/tasks.py` |
| 5 | WS 事件聚合器 + 订阅过滤（types 参数） | `central/websocket.py`、`central/events.py` |
| 6 | 前端增量渲染 + rAF 节流（替代全量刷新） | `gateway/static/bcs.js` |
| 7 | Agent 缓存清理任务 + 磁盘水位上报 + 动态背压 | `agent/worker.py`、`agent/` 新增清理模块 |
| 8 | 看门狗强杀判定改为连续超时 + 时长窗口 | Agent AdsPower 网关 |
| 9 | 心跳写分离（追加表/Redis 缓冲） | `central/devices.py` |
| 10 | max_accounts 按磁盘动态计算 | `central/accounts.py` 分配器、`agent/client.py` |

**每项改动进入对应里程碑（M1-M4）并配验证**——这些是"验证路线"的量化组成部分。

## 容量现实（需业务方知晓）

- 单台 300 Profile 的假设**未经实测且大概率不成立**（AdsPower 性能/磁盘）→ 需 S2 实测定上限
- 若实测上限 100-150：15 万账号目标需 1,000-1,500 台设备（或接受更低单台密度）
- **这是预算/目标层面的决策**，必须在 PRD v3 明确，不能留给实现兜底
