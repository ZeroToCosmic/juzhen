# 架构改进方案（500 台 × 300 账号规模）

**日期**：2026-08-11 | **前置**：`docs/架构规模审核-500x300.md`
**原则**：架构方向不变，做"实现级强化"——每项改进注明：现状（参考实现）→ 改进 → 验证方式。

---

## A. 数据层

### A1. PostgreSQL 为主库（500 规模前提）
- **现状**：`CENTRAL_DB_URL` 已支持切换；开发/小规模用 SQLite。
- **改进**：
  - 500 规模部署直接 PG（连接池 `pool_size=20, max_overflow=40`；SQLAlchemy 2 同步引擎 + 线程池已可，压力不足再切 asyncpg 异步）
  - SQLite 保留为"≤50 设备/开发"模式（附录 A 决策 2 修正）
- **验证**：S2 压测（50 设备）起全程 PG；S3 验证连接池与写延迟。

### A2. 索引策略（新增）
| 表 | 索引 | 服务对象 |
|---|---|---|
| subtasks | (tenant_id, status, priority, id) 部分索引 WHERE status IN (QUEUED, ASSIGNED, RUNNING) | 分配 TOP-N、回收器 |
| subtasks | (tenant_id, profile_id) WHERE status 活跃 | Profile 排他锁 |
| tasks | (tenant_id, status)、task_id 主键 | scheduled_tick、列表 |
| devices | (tenant_id, status, last_heartbeat_at) | 在线判定 |
| task_results | (tenant_id, created_at) | 保留/归档 |
| outbox | (status, next_attempt_at) | 中继领取 |
- **验证**：S3 下 EXPLAIN 计划 + 慢查询日志。

### A3. 保留与归档（新增，PRD D3）
- **策略**：task_results / audit_events 按月分区；归档任务（日批）把 >90 天结果迁归档表/对象存储；DLQ/attempts 保留 180 天；看板只读近 90 天。
- **验证**：S3 长期运行（模拟 30 天数据）验证库增长受控。

### A4. 租约独立化（演进）
- **现状**：租约字段内嵌 SubTask（lease_owner/generation/timeout）。
- **改进**：独立 `leases` 表（subtask_id 唯一 + generation + owner + expires_at），回收器只扫 leases 活跃行（≤1,500）→ 避免 SubTask 全表；**v1 可保持内嵌**（活跃集小），M4 抽离。
- **验证**：回收器时延指标（<500ms）。

---

## B. 调度与分配

### B1. 分配器重构：索引驱动 TOP-N + 事务认领
- **现状**：`dispatch_queued` 全表扫描 QUEUED + 内存排序。
- **改进**：单条 SQL `SELECT ... WHERE tenant_id=? AND status='QUEUED' ORDER BY priority, created_at LIMIT 50 FOR UPDATE SKIP LOCKED`（PG）；每行事务内完成"排他锁检查+分配+租约写入+Outbox"；SQLite 模式保持现状（单实例锁）。
- **验证**：S3 下 15 万账号排队时 tick 时延 <1s（压测断言）。

### B2. tick 触发改为"队列深度感知"
- **现状**：固定轮询 tick。
- **改进**：QUEUED 计数 >0 才调度（PG 轻量 count 或 outbox 事件驱动）；回收器独立周期（30s）与 API 分离进程。
- **验证**：空系统 tick 频率≈0；满负荷不丢 tick。

### B3. 定时任务错峰
- **现状**：scheduled_tick 全量扫 PENDING。
- **改进**：status 索引 + 分页；周期任务按 cron 桶（分钟粒度）触发；单时点大批量触发需错峰（每任务随机 offset 或 bucket 分片）。
- **验证**：模拟 15 万定时触发日的峰值写速率 <50/s。

---

## C. API 与 Agent 通道

### C1. 心跳节流 + 拉取合并
- **现状**：每次心跳独立 upsert + 独立拉取请求。
- **改进**：
  - 心跳 30s 窗口内重复上报合并（Agent 侧聚合：心跳即"拉取"请求，一次往返带回心跳上报+任务列表+到期时间）
  - central 侧心跳 upsert 用 `INSERT ... ON CONFLICT DO UPDATE` 原子化
- **验证**：S2 起请求速率从 100/s 降至 ~50/s；写延迟 <50ms。

### C2. 拉取间隔自适应
- **改进**：Agent 根据返回的 `next_pull_at`（= 最近租约到期时间 - 安全余量）休眠，空闲时退避到 10s；任务密集时 2s。
- **验证**：S3 空闲期 central 拉取请求率 <10/s。

### C3. 必要处异步化
- **现状**：FastAPI 同步路由（线程池）。
- **改进**：心跳/拉取/结果三热路径改 async 路由 + 异步驱动（或保持线程池并在 S3 确认线程池水位）；调度 tick 放独立进程（不与请求抢线程）。
- **验证**：S3 API P99 <100ms。

---

## D. 事件与可观测性

### D1. 事件发布保持请求内（当前已够）
- 事件量 ~20/s，请求内同步 XADD 可接受；M4 若 NATS 则移入 outbox 中继。

### D2. 指标与告警（新增，PRD D4）
| 指标 | 来源 |
|---|---|
| 写延迟/API P99 | Prometheus 直方图 |
| tick 时延、回收数、分配吞吐 | 调度器计数 |
| 队列深度（QUEUED/DLQ 计数） | DB 查询导出 |
| 心跳到达率、Agent 版本分布 | 设备表 |
| DB 增长（表大小）、连接池水位 | PG 统计 |
- 告警：写延迟 >500ms、tick >1s、DLQ 增长、心跳缺失 >90s。

### D3. 慢查询与连接池监控
- PG `pg_stat_statements` + 连接池指标导出。

---

## E. 部署形态

### E1. central 多实例（M3）
- 无状态 API × N + 独立"调度/回收"实例（抢 SKIP LOCKED）+ PG 连接池；SQLite 单实例模式保留。
- **验证**：S4 双实例扩展性（吞吐线性、无重复分配——唯一约束+SKIP LOCKED 保证）。

### E2. fake-agent 负载模拟器（关键前置工具）
- 模拟 N 台设备：心跳/拉取/执行（随机时长）/回传（随机成败）；可配置规模参数。
- **验证**：S2/S3/S4 全部规模压测依赖此工具；列入开发里程碑第一项。

---

## F. 容量模型（PRD 补齐，决定真实吞吐）

| 项 | 定义 | 影响 |
|---|---|---|
| 每账号最小动作间隔 | 如 ≥60s | 单账号吞吐上限 = 86,400/间隔 |
| 每账号日动作上限 | 如 ≤200/天 | 风控基线 + 配额校验 |
| 每台窗口并发 | 3（可配置） | 全系统峰值 1,500 |
| 全局执行节流 | 如每秒总动作 ≤50 | 防集中突发 |
| 冷却 | 2h（可配置） | PROBE/验证码恢复节奏 |

- 实现：pacing 在 Agent 执行层（现有 execution_v2 已有随机延时）+ central 侧配额校验（任务创建时校验账号剩余额度）。
- **验证**：容量模型输入 → 吞吐预估表 → 与 S3 实测对比。

## 结论

架构改进 = **数据层（PG+索引+归档）+ 分配器（TOP-N+事务认领）+ 通道（节流+自适应拉取）+ 可观测性 + 容量模型**，全部是"参考实现之上的强化"，不改变分层/状态机/租约/Outbox 架构。每条改进都有明确验证方式（S1-S4 压测 + 指标），即用户要求的"每步验证路线"的架构侧落实。
