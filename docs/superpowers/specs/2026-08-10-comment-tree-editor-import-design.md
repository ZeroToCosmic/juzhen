# 评论树编辑器与 Excel 导入设计

状态：已批准

日期：2026-08-10

关联模块：Comment Campaign 工作台

## 1. 背景

现有评论模板编辑器直接暴露 `template_id`、`step_id`、文案库 ID、文案项 ID 和 `parent_step_id`。这些字段属于内部数据契约，不是用户需要直接维护的业务信息。当前表单还把多个步骤压进狭窄的双列表格，造成以下问题：

- 用户必须理解并手工维护内部 ID。
- 评论文案、回复层级和内容来源混在同一视觉层级。
- 线性回复需要反复设置父步骤，操作成本过高。
- “请求未通过业务校验”不能指出具体错误节点。
- Campaign 创建页面要求填写模板 ID，用户无法从名称理解其含义。
- 已提前整理好的整棵评论树不能通过 Excel 预览后批量导入。

## 2. 目标

1. 用户只维护评论树名称、评论文案和回复关系。
2. 模板、节点及文案内部 ID 全部静默维护，不在常规 UI 中展示。
3. 支持手工创建完整评论树。
4. 支持从 Excel 导入多棵线性或分支评论树。
5. 默认使用线性回复，分支关系采用渐进式高级设置。
6. Campaign 按评论树名称选择模板，不再要求手工填写模板 ID。
7. 继续使用现有 CommentTemplate、CommentStep、版本快照和 Campaign 冻结机制。
8. 不迁移、不破坏既有模板与已运行 Campaign。

## 3. 非目标

- 不重构 Comment Campaign 执行器、审批、回执或队列。
- 不新增另一套与 CommentTemplate 重复的“评论树”核心实体。
- 不物理删除已被 Campaign 引用的模板。
- 不允许运行中的 Campaign 自动跟随模板新版本。
- 不在本次实现在线协同编辑、拖拽画布或无限层级可视化。
- 不引入 shadcn、React 或新的前端构建系统。

## 4. 核心决策

### 4.1 CommentTemplate 就是评论树

每个 `CommentTemplate` 直接代表一棵可执行评论树。手工创建和 Excel 导入只是两种录入方式，最终都写入现有模板、模板版本和步骤表。

不建立“模板引用评论树”的第二层抽象，避免出现以下重复关系：

```text
Campaign -> Template -> CommentTree -> Nodes
```

保留当前关系：

```text
Campaign -> CommentTemplate revision -> CommentStep tree
```

### 4.2 导入按整棵树冻结

用户选择已导入评论树时，结构、顺序、父子关系和全部文案作为一个模板版本整体使用。规划和锁定 Campaign 后继续沿用现有模板快照，不从导入文件或模板最新版本动态读取。

### 4.3 默认线性，高级模式支持分支

- 评论模式支持“独立评论”和“盖楼回复”，避免破坏现有独立评论模板。
- 独立评论中的所有节点均为同级评论，不允许设置父节点。
- 盖楼回复必须恰好有一个楼主根节点。
- 第一条是楼主评论。
- 新增回复默认指向上一条评论。
- 常规界面不显示父节点控件。
- 开启“高级分支”后，才显示“回复哪一条”。
- 父节点选择器显示人类可读标签和文案摘要，不显示节点 ID。

## 5. UI 设计

### 5.1 视觉规范

- 页面背景：`#09090B`。
- 卡片背景：`#18181B`。
- 边框：`#27272A`，统一 1px。
- 不使用纯黑或高饱和纯色。
- 字体：Inter、SF Pro 或 system-ui。
- 主信息依靠字号和间距形成层级；辅助信息使用低对比灰色。
- 圆角统一使用 12px 或 16px。
- 间距遵循 8pt 网格。
- hover 仅使用 300ms 的边框、背景和轻微位移变化。
- 不使用厚重阴影。

### 5.2 页面布局

桌面端采用 Bento 式双区域：

```text
┌────────────────────────────────────────────────────┐
│ 创建评论树                         结构有效         │
├──────────────────────────────┬─────────────────────┤
│ 单列编辑器                   │ 实时结构预览        │
│ - 评论树名称                 │ 楼主评论            │
│ - 文案来源                   │   └ 回复1           │
│ - 评论节点列表               │      └ 回复2        │
│ - 高级分支                   │ 校验摘要            │
├──────────────────────────────┴─────────────────────┤
│                                    取消  保存评论树 │
└────────────────────────────────────────────────────┘
```

窄屏时编辑器与预览改为上下排列，不出现横向滚动。

### 5.3 编辑器字段

常规字段仅包含：

- 评论树名称。
- 评论模式：“独立评论”或“盖楼回复”。
- 文案来源：“手工创建”或“已导入评论树”。
- 每个节点的评论文案。
- 高级分支开启后的父评论选择。

以下字段不得在常规 UI 中展示：

- 模板 ID。
- 节点 ID。
- 父节点 ID。
- 文案库 ID。
- 文案项 ID。
- 模板版本内部主键。

节点名称由 UI 自动派生：

- 根节点：“楼主评论”。
- 默认线性节点：“第 1 层回复”“第 2 层回复”。
- 分支节点：“回复 2”“回复 3”，并显示其父评论摘要。

### 5.4 渐进式设置

默认隐藏：

- 父评论选择。
- 语言、标签及 Profile 筛选条件。
- 模板版本和导入来源详情。

用户开启“高级分支”时，只展开父评论选择。其他高级模板元数据在独立“高级设置”折叠区中维护，不与核心文案编辑混排。

### 5.5 Campaign 创建页面

原“模板 ID”输入框替换为评论树下拉框。每项显示：

```text
评论树名称 · 5 条评论 · 版本 3
```

前端仍保存所选项的 `template_id` 和 `revision`，但不向用户展示原始 ID。

## 6. 手工创建逻辑

1. 打开编辑器时生成一个空的楼主节点。
2. 用户填写楼主文案。
3. 点击“添加下一层回复”时：
   - 静默生成新的节点 UUID。
   - 默认父节点为当前最后一条节点。
   - 自动生成可读角色名称。
   - 独立评论模式下生成同级评论，父节点始终为空。
4. 删除节点前检查是否存在子节点：
   - 无子节点：直接删除。
   - 有子节点：要求选择“同时删除后代”或取消。
   - 不自动把后代挂到其他父节点。
5. 调整顺序只改变展示顺序；父子关系仍由内部节点 ID 保存。
6. 保存前在前端执行一次完整树校验。
7. 后端使用 Pydantic 和 `validate_template_tree` 再次权威校验。

内部节点 ID 使用 `crypto.randomUUID()` 生成。编辑已有模板时必须保留既有节点 ID；只有新增节点生成新 ID。

## 7. Excel 导入

### 7.1 文件格式

首个工作表使用以下列：

| 列名 | 必填 | 说明 |
| --- | --- | --- |
| 评论树名称 | 是 | 相同名称的连续或非连续行归入同一棵树 |
| 节点序号 | 是 | 树内唯一，可使用整数或短文本 |
| 回复节点序号 | 否 | 根节点为空；线性模式下后续行为空时默认回复上一行 |
| 评论文案 | 是 | 最长 2200 字符 |

示例：

| 评论树名称 | 节点序号 | 回复节点序号 | 评论文案 |
| --- | --- | --- | --- |
| 新品讨论A | 1 |  | Has anyone tried this? |
| 新品讨论A | 2 | 1 | You gotta try it. |
| 新品讨论A | 3 | 2 | I will check it out. |
| 新品讨论A | 4 | 1 | Does it work for everyone? |

前三行形成线性链，第 4 行形成从楼主分出的第二个分支。

### 7.2 两阶段导入

阶段一：预览。

```http
POST /api/browser-v2/comment-template-imports/preview
Content-Type: multipart/form-data
```

后端使用项目已有 `openpyxl` 读取 `.xlsx`，返回：

- 文件摘要。
- 每棵树的名称、节点数和规范化节点列表。
- 树结构预览数据。
- 每棵树的错误清单。
- 是否允许提交。

预览阶段不写数据库。

阶段二：确认导入。

```http
POST /api/browser-v2/comment-template-imports
Content-Type: application/json
```

请求包含用户确认的规范化树。后端不得信任预览结果，必须重新执行字段、文本和树结构校验。

每棵树使用独立数据库事务：

- 有效树完整写入。
- 无效树完全回滚。
- 同一批次中的其他有效树不受影响。
- 响应同时返回 `created` 与 `rejected` 清单。

## 8. 数据映射

### 8.1 手工创建

现有 `TemplateCreate` 契约继续使用：

```text
UI 节点
  text                  -> fixed_text
  internal UUID         -> id
  parent internal UUID  -> parent_step_id
  source                -> content_source=fixed
  display role          -> label
```

### 8.2 Excel 导入

后端按树生成：

- `CommentTemplate.id`：UUID。
- `CommentStep.id`：UUID。
- `CommentStep.parent_step_id`：由 Excel 节点序号映射成生成后的 UUID。
- `CommentStep.position`：文件中的稳定顺序。
- `content_source`：`fixed`。
- `fixed_text`：评论文案。
- `supported_modes`：存在父子关系时为 `threaded`。

Excel 节点序号仅用于本次导入映射，不作为数据库业务 ID。

### 8.3 版本

- 新建手工树或导入树：revision 1。
- 编辑已有评论树：创建 revision + 1。
- 历史 revision 永不原地覆盖。
- Campaign 保存明确的 `template_id`、`template_revision` 和快照。

## 9. 校验规则

### 9.1 字段规则

- 名称：1 至 100 字符。
- 单棵树：1 至 100 个节点。
- 文案：1 至 2200 字符。
- 节点序号：树内唯一。
- 父节点：必须属于同一棵树。
- 根节点：盖楼树必须恰好一个；独立评论树的所有节点均为根节点。
- 禁止自引用和循环依赖。
- 固定文案节点不得同时携带文案库字段。

### 9.2 默认父节点

- 第一行父节点必须为空。
- 后续行未填写“回复节点序号”时，默认回复同一树中的上一行。
- 显式填写父节点时，使用填写值。
- 父节点可以位于文件后方，但预览必须通过完整图校验后才能提交。

### 9.3 用户错误提示

前端把后端稳定错误映射为带位置的中文信息：

| 错误码 | UI 提示示例 |
| --- | --- |
| `tree_name_missing` | 第 3 行缺少评论树名称 |
| `node_no_missing` | 第 7 行缺少节点序号 |
| `duplicate_node_no` | 评论树“新品讨论A”存在重复节点 2 |
| `comment_text_missing` | 第 5 行评论文案为空 |
| `comment_text_too_long` | 第 9 行评论文案超过 2200 字符 |
| `parent_not_found` | 节点 4 引用了不存在的父节点 8 |
| `root_count_invalid` | 盖楼评论树必须恰好有一个楼主节点 |
| `cycle_detected` | 节点 3 与节点 5 形成循环回复 |
| `tree_too_large` | 单棵评论树最多包含 100 条评论 |

通用的 `template_invalid` 继续保留为后端防御性错误，但编辑器不得只显示“请求未通过业务校验”。

## 10. 接口兼容

以下现有接口保持不变：

- `GET /api/browser-v2/comment-templates`
- `POST /api/browser-v2/comment-templates`
- `GET /api/browser-v2/comment-templates/{template_id}`
- `PUT /api/browser-v2/comment-templates/{template_id}`
- `POST /api/browser-v2/comment-templates/{template_id}/disable`

新增接口仅负责 Excel 导入：

- `POST /api/browser-v2/comment-template-imports/preview`
- `POST /api/browser-v2/comment-template-imports`

所有写接口继续遵守：

- 严格 JSON 或 multipart 边界。
- 拒绝未知字段。
- 编辑使用 `expected_revision` CAS。
- 成功响应使用 `{ "data": ... }`。
- 错误响应使用 `{ "error": { "code": ..., "message": ... } }`。
- Legacy 模式继续使用管理认证、角色和 CSRF。
- Local-direct 模式继续使用 loopback 与 Host 防护。

## 11. 错误与恢复

- Excel 文件损坏：返回固定 `import_file_invalid`，不写数据库。
- 文件类型不支持：返回 `unsupported_import_type`。
- 文件过大：返回 413 `import_file_too_large`。
- 单树校验失败：放入 `rejected`，不影响其他树。
- 数据库创建失败：该树事务回滚，返回固定 `import_tree_failed`。
- 浏览器请求中断：重新加载评论树列表即可对账；不自动重复提交未确认批次。
- 编辑 revision 冲突：返回 409，UI保留草稿并要求刷新后重新应用。
- Campaign 已冻结旧版本：模板编辑成功也不得修改 Campaign 快照。

## 12. 安全边界

- Excel 只解析 `.xlsx`，不执行宏、公式或外部链接。
- 解析时使用 `openpyxl` 的只读模式和 `data_only=True`。
- 限制文件大小、工作表数量、行数和单元格文本长度。
- 错误响应不回显本地路径、堆栈或完整文件内容。
- UI使用 `textContent` 渲染预览文案，不拼接用户输入 HTML。
- 不把模板内容、Campaign数据或导入文件写入 `localStorage`。
- API 可以传输内部模板和节点 ID，但常规 UI、通知和错误文案不得展示这些 ID。

## 13. 迁移方案

本设计不需要修改核心数据库表。

既有数据处理：

1. 保留所有模板、revision 和步骤记录。
2. 新 UI 读取既有步骤 ID，但只在内存状态和 API 请求中使用。
3. 根据根节点、父子关系和 position 生成可读层级名称。
4. 旧的 `step_1` 等字符串 ID不需要改为 UUID。
5. 新建节点开始使用 UUID。
6. 已运行 Campaign 继续使用历史快照。
7. 已停用模板仍可查看，但不可用于新 Campaign。

## 14. 测试与验收

### 14.1 前端测试

- 页面不渲染模板 ID、节点 ID、文案库 ID和文案项 ID输入框。
- 默认新增节点自动回复上一节点。
- 开启高级分支后才显示父评论选择。
- 删除有后代节点时不会静默重挂父节点。
- 轮询刷新不清空正在编辑的评论树草稿。
- Campaign 使用名称下拉框选择模板。
- 前端错误能显示树名、行号和节点号。
- 所有用户文本使用安全文本节点渲染。
- 736px 与 360px 宽度无横向溢出。

### 14.2 后端测试

- 手工线性树、星型树和多分支树通过。
- 空文案、多根、缺父节点、自引用和循环被拒绝。
- 导入多棵树时有效树成功、错误树完整回滚。
- Excel空父节点按上一行映射。
- Excel显式父节点形成正确关系。
- 同一文件中树名混排仍正确分组。
- 文件损坏、超限和不支持格式均为固定错误。
- 编辑仍使用 revision CAS。
- 已冻结 Campaign 不受模板新 revision影响。
- Local-direct 与 Legacy 认证回归通过。

### 14.3 完成标准

1. 用户创建评论树全程无需输入或复制任何 ID。
2. 手工线性树只需填写名称和逐条文案。
3. 分支树可以通过“回复哪一条”正确建立。
4. Excel导入前能看到完整树预览和逐行错误。
5. 无效树不会留下部分数据库记录。
6. Campaign 可以通过评论树名称完成选择、规划和冻结。
7. 所有既有模板和 Campaign 继续可读、可运行。
