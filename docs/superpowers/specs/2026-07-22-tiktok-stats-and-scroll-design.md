# TikTok 数据统计与滚动次数设计

日期：2026-07-22

## 目标

在现有 Flask 主控系统中加入独立的 TikTok 账号统计能力，并以本地部署的
[`Evil0ctal/Douyin_TikTok_Download_API`](https://github.com/Evil0ctal/Douyin_TikTok_Download_API)
作为采集基础。系统面向 50–500 个 TikTok 账号，每 3 小时进行增量采集，按
`Asia/Shanghai` 自然日生成永久保存的每日汇总。

同时把执行策略中的向上/向下滚动参数改成明确的“最小滚轮次数”和“最大滚轮
次数”。每轮执行时从范围内随机选择整数，并严格生成对应数量的合成滚轮事件。

## 已确认的产品决策

- 跟踪规模：50–500 个账号。
- 采集频率：每 3 小时一次。
- 每日增量：当天最后一个完整快照减去前一天最后一个完整快照；负数保留。
- 账号来源：支持独立导入用户名，也可从现有账号库勾选加入。
- 默认页面：表格优先；账号卡片作为详情页；日期×账号矩阵作为趋势页。
- 保留周期：3 小时快照保留 90 天，每日汇总永久保留。
- Cookie：在统计设置页手动录入，脱敏显示并加密保存。
- 作品范围：每 3 小时获取账号资料和最新作品；每天分批完成全部作品校准。
- 滚动次数：保存最小值和最大值，每轮随机采样。

## 范围

### 本期包含

- 独立部署第三方 TikTok API 服务。
- TikTok Cookie 配置、有效性检测和服务状态展示。
- 用户名/主页链接导入、现有账号勾选、去重、停用和恢复。
- `uniqueId` 到 `secUid` 的解析与缓存。
- 三小时增量采集、每日全部作品校准、重试、限速和任务状态。
- SQLite 统计存储、90 天快照清理、永久日汇总。
- 默认统计表格、账号详情和趋势矩阵。
- 单日/日期范围筛选，作品/点赞/浏览/评论升降序排序，搜索和分页。
- 滚动动作参数文案、表单、验证和回归测试。

### 本期不包含

- 向公网开放第三方 API 或统计 API。
- 自动从 AdsPower 读取 Cookie。
- 抓取私密账号、绕过验证码或绕过平台访问控制。
- 用第三方项目替换现有发布结果采样链。
- 为其他社交平台复用本期统计数据库。
- 把第三方项目依赖安装进主系统 Python 3.13 虚拟环境。

## 总体架构

采用“主应用 + 统计采集器 + 第三方爬虫服务”的三个边界：

```text
浏览器统计页面
    ↓ HTTP
现有 Flask 网关
    ├─ 统计查询与账号管理 API
    ├─ 加密 Cookie 设置 API
    └─ SQLite 统计仓储
            ↑
      独立统计采集进程
            ↓ loopback HTTP
Docker: Douyin_TikTok_Download_API (Python 3.11)
            ↓
          TikTok
```

第三方项目固定到一次明确解析出的完整 Git 提交 SHA；安装记录写入本地版本文件。
后续启动只使用已记录版本，不自动跟随 `main` 或 Docker `latest`。第三方服务绑定
`127.0.0.1` 的非特权端口，主应用通过适配器调用：

- `GET /api/tiktok/web/fetch_user_profile`
- `GET /api/tiktok/web/get_sec_user_id`
- `GET /api/tiktok/web/fetch_user_post`

第三方服务仅负责返回当前数据，不负责历史记录、每日差值、账号队列或页面展示。

## 部署与运行

### 安装位置

- 第三方源码与版本记录放在项目内独立服务目录，不加入主应用包导入路径。
- Docker 构建使用第三方项目声明的 Python 3.11 基础镜像。
- 服务端口不使用第三方默认的主机 80 端口，改为独立 loopback 端口。
- 统计数据库位于 `data/stats/tiktok_stats.db`。
- 运行期 Cookie 配置位于仅当前 Windows 用户可读的目录，不提交到版本控制。

### 本机准备

- Docker Desktop 已安装并启动，当前用户可以访问 Docker Engine。
- 本机或代理出口能够正常访问 TikTok。
- 用户提供一个已登录 TikTok Web 会话的有效 Cookie。
- 主系统、统计采集器和第三方容器使用同一台本机的可靠时钟。

### Cookie 处理

- 浏览器只向保存接口发送一次 Cookie，后续 GET 不返回原文。
- Windows 上使用当前用户范围的 DPAPI 加密后落盘。
- 页面只显示“未设置、有效、失效、待验证”和最近验证时间。
- 写日志、任务错误和第三方响应样本前统一清除 Cookie、token 和请求头。
- 保存新 Cookie 后更新第三方服务的运行期配置并重新启动容器；重启失败时保留旧的
  加密配置和清晰的操作状态，不宣称新 Cookie 已生效。

## 数据模型

SQLite 启用外键、事务和 WAL。所有时间以 UTC 保存，按 `Asia/Shanghai` 转换为业务
日期。

### `tracked_accounts`

- `id`：内部稳定 ID。
- `username`：保留显示大小写的规范用户名。
- `username_key`：去除 `@` 后的小写唯一键。
- `sec_uid`：TikTok 稳定用户标识，可在用户名变化后继续使用。
- `source`：`import` 或 `existing_account`。
- `source_account_id`：可空，关联现有账号库中的账号 ID。
- `enabled`：是否参与调度。
- `profile_status`：`pending`、`active`、`not_found`、`private`、`error`。
- `last_success_at`、`last_error_code`、`last_error_message`。
- `created_at`、`updated_at`。

### `collection_runs`

- `id`、`run_type`（`incremental` 或 `full`）。
- `scheduled_for`、`started_at`、`finished_at`。
- `status`：`queued`、`running`、`complete`、`partial`、`failed`。
- 账号总数、成功数、失败数、重试数。
- 单例租约字段，保证同一计划周期只有一个采集进程执行。

### `account_snapshots`

- 账号 ID、采集时间、业务日期、关联运行 ID。
- `coverage`：`profile_recent` 或 `full`。
- 当前作品数、账号累计获赞、粉丝数、关注数。
- 已覆盖作品数、作品点赞合计、浏览合计、评论合计。
- 数据源版本和解析器版本。
- `(account_id, collected_at, coverage)` 唯一。

三小时快照保留 90 天。清理任务只删除过期快照，不删除每日汇总、当前作品状态或
采集运行审计。

### `posts_current`

- 账号 ID、作品 ID、发布时间、最后发现时间。
- 当前点赞、浏览、评论、分享指标。
- `is_deleted`、`deleted_detected_at`。
- 原始标题只保存用户可见且统计页需要的截断文本，不保存下载地址或媒体文件。
- `(account_id, post_id)` 唯一。

### `daily_account_metrics`

- 账号 ID、业务日期、对应完整快照 ID。
- 当日最终作品数、点赞、浏览和评论总量。
- 相对前一完整业务日的四项增量；允许负数。
- `baseline_status`：`ready`、`first_day`、`missing_previous`、`incomplete`。
- `(account_id, business_date)` 唯一。

第一次完整校准只建立基线，不生成虚构的日增量。如果当天或前一天缺少完整快照，
该日显示“数据不完整”或“暂无对比”。

## 账号导入

支持 TXT、CSV、TSV 文本以及从当前 SQLite 账号库勾选加入。输入接受：

- `username`
- `@username`
- `https://www.tiktok.com/@username`

导入流程先规范化和去重，再写入跟踪列表。解析任务异步获取资料与 `secUid`，单个
账号失败不回滚其他合法账号。重复账号返回“已存在”，不会创建第二条记录。停用账号
停止新采集但保留全部历史；恢复后继续使用原账号 ID 和 `secUid`。

## 调度与采集

### 三小时增量任务

- 按 `Asia/Shanghai` 每 3 小时创建一轮任务。
- 在周期内给账号加入稳定随机抖动，避免同时请求。
- 获取账号资料，并分页获取最新作品，直到遇到已知作品或达到安全页数。
- 写入 `profile_recent` 快照和最新作品状态。
- 增量快照不冒充完整账号浏览/评论总量，不用于生成每日最终值。

### 每日完整校准

- 每个自然日将所有启用账号分批排入完整校准队列。
- 对每个账号分页读取全部可见作品并计算完整合计。
- 单账号成功后原子写入完整快照、当前作品状态和当日日汇总。
- 只有该账号完成全量采集后，才替换其当日完整结果。
- 某账号失败不阻塞其他账号；该账号显示不完整并在后续周期补采。

### 限速与重试

- 使用小并发工作池和每账号串行请求。
- 请求间隔带随机抖动。
- 网络错误、超时和服务端临时错误使用有限次数指数退避。
- 用户不存在、私密账号、Cookie 失效和结构不兼容不做无限重试。
- Cookie 失效会打开全局采集熔断，停止创建新请求并提示更新 Cookie。

## 统计查询语义

- 单日模式读取该日 `daily_account_metrics`。
- 日期范围模式使用结束日最终值减去开始日前一完整日最终值；同时可读取逐日序列。
- 排序字段白名单：`posts_delta`、`likes_delta`、`views_delta`、
  `comments_delta`。
- 每个字段支持升序和降序，默认 `views_delta desc`。
- 服务器执行搜索、完整性筛选、采集状态筛选、排序和分页。
- 空值不转换为零；缺失对比值在排序时位于有效数据之后。
- 负数原样返回，由页面使用红色和原因提示展示。
- 查询接口纯读取；页面刷新不得启动采集或改写数据。

## 页面设计

### 默认统计表格

工具栏包含单日/日期范围、账号搜索、采集状态、数据完整性、排序字段、升降序和
分页大小。操作入口包含“立即采集”“导入账号”“统计设置”。

汇总卡显示跟踪账号数、完整采集账号数、新增作品、点赞、浏览、评论，以及失败或
不完整账号数量。

表格列包含账号、采集状态、最后成功时间、四项日增量、当前作品数和完整性。负数
标红，首次基线显示“暂无对比”，不完整数据不显示为零。

### 账号详情

展示当前总量、最近采集状态、每日增长折线、作品列表、增长最快作品、疑似删除作品
和采集错误历史。

### 趋势页

展示日期×账号矩阵，可切换作品、点赞、浏览、评论；支持日期范围和账号搜索。点击
单元格进入对应账号与日期详情。

账号导入与 Cookie 设置独立于结果页。统计页加载只查询数据。

## 滚动动作

现有 canonical runtime 已通过 `total_count=[min,max]` 从范围内随机采样，并循环
调用 `page.mouse.wheel`。本期不升级策略 schema。

前端对 `scroll_up` 和 `scroll_down` 显示：

- 每次滚动距离。
- 最小滚轮次数。
- 最大滚轮次数。
- 最小间隔秒数。
- 最大间隔秒数。

保存时将两个次数继续序列化到 `total_count`。最小值和最大值均为正整数，且最小值
不得大于最大值。每轮执行只采样一次次数，并严格生成对应数量的合成滚轮事件。

`burst_count` 当前不产生独立的组间节奏，因此新动作默认 `[1,1]`，普通表单不展示。
编辑旧策略时保留原值，不因隐藏字段而覆盖。这里的“次数”指浏览器合成滚轮事件数，
不宣称等同于物理鼠标硬件刻度。

## API 边界

新增统计 API 分为：

- 跟踪账号：列表、导入、从现有账号加入、启用、停用。
- 采集设置：读取脱敏状态、保存 Cookie、验证连接、读取调度状态。
- 采集任务：立即创建增量任务、读取任务与账号错误。
- 统计查询：汇总表、账号详情、趋势矩阵和作品详情。

所有写接口验证 JSON 对象、账号标识和权限边界。Cookie 原文只允许进入保存接口，
禁止进入响应、任务表、统计表和日志。

## 失败处理

- 第三方容器不可用：采集任务进入失败/等待状态，历史查询继续可用。
- Cookie 无效：停止新采集，保留历史，设置页明确提示更新。
- 单账号请求失败：记录稳定错误码并继续其他账号。
- 第三方响应结构变化：契约校验失败，不写部分数据；保存已脱敏的结构摘要用于排查。
- 全量分页中断：不替换当日完整快照，保留上一次完整数据并标记不完整。
- 数据库写入失败：事务回滚，任务不得显示成功。
- 重复 worker：数据库租约只允许一个调度者；过期租约可安全接管。

## 安全与合规

- 服务只绑定 loopback，不提供公网访问。
- Cookie 使用当前 Windows 用户的 DPAPI 加密保存。
- 日志和错误样本清除 Cookie、Authorization、token 和代理凭证。
- 不把第三方仓库内示例 Cookie 当作可用凭证。
- 只采集用户有权跟踪的公开账号数据，遵守适用的平台条款、速率限制和法律要求。
- 保留第三方 Apache-2.0 许可证和归属文件。

## 测试策略

### 第三方适配器

- 使用固定响应夹具验证资料、`secUid`、作品分页和指标解析。
- 验证超时、HTTP 错误、Cookie 失效、私密/不存在账号和结构变化。
- 自动化测试不得依赖真实 TikTok 或真实 Cookie。

### 仓储与汇总

- SQLite 建表、升级、唯一约束、事务回滚和 WAL。
- 首日基线、正常正增量、负增量、缺前日、全量失败和补采覆盖。
- 90 天快照清理不删除日汇总。
- 并发 worker 租约与同一轮幂等。

### 调度

- 三小时间隔、`Asia/Shanghai` 日期边界、随机抖动和有限重试。
- 增量任务不生成完整日汇总。
- 全量分页全部成功后才提交完整结果。

### API 与页面

- 导入格式、规范化、去重、停用/恢复。
- 单日/日期范围、四种排序、升降序、稳定二级排序和分页。
- 空数据、负值、缺失值、采集失败与 XSS 转义。
- 页面 GET/刷新无采集和写入副作用。
- Cookie 保存失败不得显示“已保存”；GET 永不返回原文。

### 滚动动作

- 表单将最小/最大次数正确序列化为 `total_count`。
- 保存后刷新和进程重启仍保留次数范围。
- 固定 RNG 下执行次数位于范围内并与 wheel 调用数严格一致。
- 上下方向符号正确；非法范围在保存前后均被拒绝。
- 隐藏 `burst_count` 后编辑旧策略不覆盖原值。

## 验收标准

- 本地第三方服务与主系统依赖隔离并可独立健康检查。
- 50–500 个账号可以导入、去重、停用、恢复并查看采集状态。
- 三小时任务与每日完整校准不会因页面刷新重复执行。
- 第二个完整业务日起可以准确显示四项日净变化，负数和缺失值不被隐藏。
- A 表格、B 详情、C 趋势均使用同一日汇总口径。
- 日期筛选、四种指标排序、升降序、搜索和分页可用。
- Cookie 不出现在页面响应、日志、数据库或版本控制中。
- 滚动动作可以配置随机次数范围，并严格执行采样次数。
- 全量 Python、Node、API、页面和数据库测试通过。

## 安装前仍需用户准备

- 启动 Docker Desktop，并修复当前 Docker Engine 访问权限。
- 提供有效的已登录 TikTok Web Cookie。
- 确认本机或代理出口可以稳定访问 TikTok。
- 如果 Git 的 Windows 凭证链仍无法访问 GitHub，允许安装流程改用 GitHub 源码归档下载，
  并用 SHA-256 和记录的提交 SHA 固定来源。
