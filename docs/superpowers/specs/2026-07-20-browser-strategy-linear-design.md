# 浏览器接管与线性执行策略设计

## 目标

本次改造解决两个问题：

1. AdsPower 窗口打开后没有稳定导航到默认网址，导致执行策略在 blank 页或旧 Tab 上运行。
2. 执行策略配置项分散在网格中，无法直观表达“停留 → 滚动 → 暂停 → 有序点击 → 输入文案 → 提交 → 循环”的执行流程。

同时，Windows 窗口平铺需要保证窗口不重叠、面积按窗口数量均分，并将已打开窗口提升到桌面前层。

## 现状与根因

- `browser.default_url` 已支持默认值 `https://www.tiktok.com/`。
- `/api/browser/open-tile` 会在启动后导航，但 `/api/browser/execute-strategy` 当前直接执行策略，没有在策略开始前重新同步网址和清理 Tab。
- 配置页同时展示了 `browser.cdp_url` 和 `adspower.base_url`，容易把 AdsPower Local API 地址误填到 CDP 地址字段。AdsPower 模式应使用 `adspower.base_url` 与 API Key，`ws.puppeteer` 由启动接口临时返回。
- 当前自动策略运行时已经具备随机时长、停留、滚动阈值、暂停、顺序点击、内容库抽取和输入验证的基础结构，但需要加强页面导航前置条件及文案在页面中的可见验证。
- 当前窗口位置计算使用规则网格；需要改为按窗口数量生成互不重叠的等面积区域，并在 `SetWindowPos` 后提升窗口层级和校验矩形。

## 方案

采用保留现有配置格式、重构执行流程和页面布局的方案，不新增数据库表，不删除已有策略字段。

### 1. 默认网址与 CDP 流程

策略执行前，对每一个选中窗口执行以下步骤：

1. 从活动会话取得 `ws.puppeteer`。
2. 等待 CDP 地址可连接；失败时返回 profile 级错误，不执行动作。
3. 使用现有 Tab 同步函数导航到 `browser.default_url`；没有配置时使用 `https://www.tiktok.com/`。
4. 关闭除目标 Tab 外的其他 Tab。
5. 验证当前页面不是 `about:blank`，并验证页面 URL 已进入目标网址或其合法重定向地址。
6. 只有前置流程成功后才调用自动策略运行器。

打开窗口接口继续保留原有导航流程，策略执行接口增加同样的前置同步流程，确保用户直接执行策略时也不会在旧页面或 blank 页上运行。

配置页将把字段说明调整为：

- `AdsPower API 地址`：AdsPower Local API，例如 `http://local.adspower.net:50325`。
- `手动 CDP 地址`：仅用于非 AdsPower 的手动 Chrome 调试模式；AdsPower 模式留空。
- `浏览器默认网址`：默认 `https://www.tiktok.com/`。

不会把 `ws.puppeteer` 保存到配置文件；它只在 AdsPower 启动后由后端使用。

### 2. 自动策略运行模型

继续使用现有 `browser.auto_strategies` 配置，字段含义如下：

```text
total_duration_minutes       总执行时长范围，默认 [3, 5]
stay_seconds                 初始及轮次间停留范围，默认 [3, 10]
scrolls_per_round            每个滚动小段的动作次数，默认 [1, 3]
scroll_interval_seconds      每次滚动间隔，默认 [1, 3]，抽样后保留两位小数
scroll_threshold              累计滚动阈值，默认 [30, 50]
pause_seconds                达到阈值后的暂停范围，默认 [3, 10]
scroll_distance              单次滚动距离
click_elements               已排序的元素别名数组
input_element                输入框元素别名
submit_element               输入完成后的提交元素别名
comment_brand_id             内容管理文案库；为空时从全部文案随机抽取
batch_size                   批量窗口数量，范围 1～8
```

每个窗口每次运行只抽样一次总时长；每轮重新抽样滚动次数、滚动阈值和暂停时长；达到阈值后将滚动计数清零并进入下一轮，直到达到总时长。

### 3. 强验证规则

- 点击前验证 XPath 元素存在且可见；点击调用无异常才记录为已点击。
- 输入前验证输入元素存在且可见；逐字输入文案，随后读取输入值确认完整文案存在。
- 输入后同时检查输入控件值和页面文本；至少有一个位置包含完整文案，否则判定输入验证失败。
- 提交元素必须存在、可见且点击成功。
- 每轮返回已点击元素、输入文案、验证状态和失败步骤；任何失败都以 profile 为粒度记录到浏览器后台日志。

### 4. 线性配置页面

自动策略管理区域改成单列竖向步骤，每个步骤一行，步骤顺序与执行顺序一致：

1. 策略名称与总时长。
2. 初始停留时间。
3. 每轮滚动次数和滚动间隔。
4. 累计滚动阈值和单次距离。
5. 达到阈值后的暂停时间。
6. 有序点击元素列表。
7. 内容库选择。
8. 输入框与提交按钮。
9. 批量窗口数量。

网页元素列表继续支持自定义名称、XPath 编辑、删除和上移/下移。元素顺序明确显示序号，并直接作为 `click_elements` 的引用顺序。保存后的配置仍通过现有 `/api/browser/auto-strategies` 和 `/api/browser/action-config` 接口持久化。

### 5. Windows 窗口平铺与前层显示

窗口平铺器继续限制最多 8 个窗口，并使用 Windows 工作区尺寸。对于 N 个窗口生成 N 个互不重叠的矩形，每个矩形面积为工作区面积的 `1/N`；优先选择接近方形的分行方案，无法整除时使用等面积的非等高行。

每个窗口执行：

1. `SW_RESTORE` 恢复窗口。
2. `SetWindowPos(HWND_TOP, ...)` 设置位置和大小，不使用 `SWP_NOZORDER`。
3. `BringWindowToTop` 和 `SetForegroundWindow` 提升到桌面前层，但不设置永久置顶。
4. `GetWindowRect` 回读校验；不一致时重试一次并记录失败原因。

### 6. 错误处理与日志

每个 profile 的失败结果包含：

- profile_id；
- 阶段：CDP、导航、Tab 清理、元素定位、点击、输入或验证；
- 尝试次数；
- 原始异常信息；
- 目标网址。

GUI 继续提供 `/api/browser/logs` 查询入口。窗口导航失败时不报告“策略执行成功”，并将该窗口标记为失败。

## 测试计划

先写测试再实现：

1. API 测试：执行策略前会调用默认网址导航；未提供 URL 时使用 TikTok 首页；导航失败时不调用策略运行器。
2. CDP 测试：模拟 CDP 未就绪后恢复，确认导航继续执行；模拟超时，确认返回 profile 级错误。
3. 运行时测试：确认抽样范围、滚动计数重置、输入值和页面文本验证、顺序点击及总时长停止。
4. UI 测试：确认线性步骤结构、默认值、CDP 字段说明和元素排序控件存在。
5. 平铺测试：确认 N 个窗口无交集、面积等于工作区面积的 `1/N`，并调用窗口前层 API。
6. 完成后运行全部 Python 测试、Node 测试和 Python 语法检查。

## 验收标准

- 选中窗口执行策略时，每个窗口都会先打开并清理到默认 TikTok 首页。
- 任意窗口导航失败时，该窗口不执行策略，并能在后台日志中定位原因。
- 配置页面按照实际执行顺序从上到下显示，每个步骤的参数可单独编辑和保存。
- XPath 元素可以排序，策略按保存的顺序点击。
- 文案随机来自内容管理文案库，并完成输入及页面可见性验证。
- 1～8 个窗口均不重叠，4 个窗口时为四等分平铺，并显示在桌面前层。
