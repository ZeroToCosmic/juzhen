# Browser V2 TikTok 滚轮校准设计

日期：2026-08-06（2026-08-07 增补自动回放验收）  
状态：已完成方案评审，等待规格复核

## 1. 背景

Browser V2 当前使用 Playwright `page.mouse.wheel(0, 120)` 驱动 TikTok 视频切换，并通过视频身份变化判断成功。真实运行中，两个测试 Profile 都返回 `video_switch_not_observed`。

Windows 鼠标消息中的 `WHEEL_DELTA=120` 是硬件滚轮动作单位；Playwright `mouse.wheel()` 接收的是页面滚轮事件增量，语义并不相同。继续固定发送 `120` 或快速补发多个脉冲，既不能保证触发 TikTok 的切换阈值，也会造成页面抖动和不自然行为。

## 2. 目标

- 使用一次真实鼠标单格滚动产生的浏览器事件作为执行依据。
- 连续采集三次单格滚动，只有结果一致时才发布校准版本。
- 正式执行每切换一个视频只回放一组校准事件，不使用人为 burst。
- 回放后必须观察到且仅观察到一个视频稳定切换。
- 三次人工采样后必须通过一次自动单事件回放，才能发布校准版本。
- 校准失败不覆盖上一已通过自动回放验收的有效版本。
- 单个 Profile 执行失败不影响同批其他 Profile。

## 3. 非目标

- 不实现 Windows 全局鼠标钩子或 `SendInput`。
- 不把滚轮数据混入页面元素定义。
- 不修改五类积木动作的组合模型。
- 不恢复固定像素范围或用户可编辑滚动距离。
- 正式策略执行失败后不补发滚轮；校准阶段只允许按固定倍率逐个验证候选值。

## 4. 方案选择

采用 V2 原生校准。复用 V2 的 Profile 解析、AdsPower 启停、Playwright 会话、页面就绪检测和 Profile 租约，不依赖旧执行模块的行为录制接口。

未采用的方案：

- 扩展旧行为录制器：旧录制器只支持鼠标轨迹和键盘节奏；让 V2 依赖旧窗口状态会重新产生跨模块耦合。
- Windows 原生输入：需要处理系统权限、焦点、窗口坐标和多窗口并发，超出本次最小可靠修复范围。

## 5. 页面交互

滚轮校准入口放在“元素库 → 页面点选器”，复用现有“测试 Profile”和“目标网址”输入。

按钮区增加“滚轮校准”：

```text
测试 Profile    目标网址

[开始点选器] [滚轮校准] [完成点选] [取消当前操作]
```

点选器与校准是互斥模式：

- 点选器运行时不能启动校准。
- 校准运行时不能启动点选器。
- 校准时不注入元素点击捕获，防止用户滚动时误选元素。
- “取消当前操作”根据当前模式取消点选或校准。

校准状态显示：

- 当前阶段：准备页面、等待第 1/3 次、确认切换、等待第 2/3 次、确认切换、等待第 3/3 次、发布成功或失败。
- 明确提示：“请将鼠标放在视频区域，向下滚动一格”。
- 三个采样结果格：待操作、验证中、通过或失败。
- 当前有效版本、校准时间、事件数量。
- 对用户显示固定中文错误，不暴露 WebSocket、Profile 原始 ID、Cookie 或内部异常文本。

## 6. 校准采集

开始校准后，V2 使用所选 Profile 打开目标网址，等待 TikTok 视频流就绪，然后在页面捕获阶段监听 `wheel` 事件。

每个物理滚轮动作按以下规则形成一个事件组：

- 只接受 `event.isTrusted === true` 的事件。
- 保存 `deltaX`、`deltaY`、`deltaMode` 和相邻事件时间差。
- 只接受 `deltaMode === 0` 的像素型事件；其他模式不能无损映射到 Playwright 的像素增量，校准应明确失败而不是猜测换算。
- 连续 180ms 没有新 wheel 事件，视为本次滚动结束。
- 不保存事件目标文本、视频内容、账号、Cookie 或 Profile ID。

每次采样开始前记录当前视频身份；事件组结束后持续轮询视频身份直到页面稳定。系统记录期间出现的去重身份序列，只有发生一次身份迁移且新身份稳定时才接受该样本，不能仅比较首尾身份。

三次样本必须满足：

- 方向相同。
- 每次恰好切换一个视频。
- 三次总 `deltaY` 的偏差不超过 20%。

真实鼠标的一格滚动可能被浏览器拆成不同数量的 wheel 事件，因此事件数量不作为一致性条件。通过后选择“总 `deltaY` 最接近三次中位数”的样本作为基础值。人工采样只证明真实鼠标输入有效，不能直接发布；发布前还必须完成下述自动回放验收。

每次样本完成单视频切换后，界面显示“视频切换成功”，避免把单样本成功误解为三样本最终一致性已通过。最终一致性失败时显示固定中文说明、继续使用的旧版本号，以及三个样本的脱敏统计（事件数量和总 `deltaY`），不显示页面内容或 Profile 身份。

### 6.1 自动单事件 Dry-Run

三次人工样本一致后，以代表样本的总 `deltaY` 为基础值，依次验证倍率 `1.0`、`1.5`、`2.0`、`3.0`。每个候选只调用一次 `page.mouse.wheel(0, candidate_delta_y)`；不回放多个快速事件，不使用 burst。

每次候选验证遵守以下规则：

1. 记录当前视频身份，把鼠标移动到视频流容器中心。
2. 只发送一个候选 wheel 事件。
3. 最多等待 8 秒，观察视频身份变化并稳定。
4. 恰好切换一个视频时立即停止搜索，将该候选值发布为一个单事件回放版本。
5. 没有切换时，必须确认原视频身份重新稳定，才可测试下一个倍率；页面未稳定则立即失败。
6. 观察到跨越多个视频时立即失败，不再尝试更大倍率。
7. 四个倍率都未命中时失败，不发布版本。

校准候选之间是独立、可观察的验证，不是策略执行时的失败重试。正式策略仍只发送已验证版本中的一个 wheel 事件，失败后不补发。

活动会话公开状态增加候选序号、倍率、候选 `deltaY` 和结果（未切换、单视频切换、跨越多个视频）。这些字段只用于诊断，不保存页面文本、视频身份或 Profile ID。

## 7. 数据模型

校准数据保存在 V2 SQLite。新增单一作用域 `tiktok_feed` 的版本化记录，至少包含：

```json
{
  "scope": "tiktok_feed",
  "revision": 1,
  "status": "validated",
  "direction": "down",
  "events": [
    {
      "delta_x": 0,
      "delta_y": 100,
      "delta_mode": 0,
      "delay_ms": 0
    }
  ],
  "sample_count": 3,
  "replay_validated": true,
  "created_at": "2026-08-06T00:00:00Z"
}
```

校准会话状态只保存在服务进程内；最终验证版本持久化。`wheel_calibrations` 增加 `replay_validated` 布尔列，默认值为 `false`。升级前产生的旧版本因此不能再供策略执行；用户完成一次新校准后才产生可执行版本。发布使用单个 SQLite 事务：先插入 `replay_validated=true` 的新版本，再切换当前有效版本。事务失败时旧记录保持不变，但只有通过自动回放验收的版本可被读取为当前执行版本。

## 8. HTTP 边界

新增三个 V2 接口：

- `GET /api/browser-v2/wheel-calibration`：返回当前有效版本和活动会话公开状态，供页面轮询。
- `POST /api/browser-v2/wheel-calibration/start`：接收 `profile_token` 和 HTTPS `target_url`，异步开始校准。
- `POST /api/browser-v2/wheel-calibration/cancel`：取消当前活动校准。

同一时间只允许一个活动校准会话。活动 Profile 必须取得 V2 租约，不能同时参与执行任务或点选器。校准成功、失败或取消后，都关闭本次浏览器窗口并释放会话与租约。

## 9. 执行接线

滚动动作执行前读取 `tiktok_feed` 的当前 `validated` 校准版本：

1. 捕获当前视频身份。
2. 将鼠标移动到当前视频的可滚动区域。
3. 使用 `page.mouse.wheel()` 回放经过 Dry-Run 验证的单个事件。
4. 等待视频身份变化并稳定。
5. 成功后记录完成一次视频切换；失败时停止当前 Profile。

一个策略请求切换多次时，每次只回放一个已验证事件，并遵守动作配置的切换间隔范围。不得因一次失败而补发额外事件。

执行结果记录：

- `calibration_revision`
- `requested_switches`
- `completed_switches`
- `wheel_events`
- 每次切换前后的脱敏视频身份

若策略包含滚动动作但没有有效校准版本，任务在打开 Profile 前失败，避免无意义地启动几百个窗口。

## 10. 错误语义

- `wheel_calibration_missing`：没有有效校准版本。
- `wheel_calibration_inconsistent`：三次总位移差异超过允许范围；事件数量不同本身不再导致失败。
- `wheel_calibration_unsupported_delta_mode`：浏览器报告的滚轮单位无法无损回放。
- `wheel_calibration_video_not_changed`：校准滚动没有切换视频。
- `wheel_calibration_multiple_videos`：一次滚动跨越多个视频。
- `wheel_calibration_context_lost`：校准窗口或页面上下文失效。
- `wheel_calibration_replay_not_observed`：四个自动单事件候选均未切换视频。
- `wheel_calibration_replay_unstable`：候选失败后页面未恢复到原视频稳定状态，不能安全继续测试。
- `calibrated_video_switch_not_observed`：正式执行回放后没有观察到视频切换。

校准错误只影响校准会话；执行错误只影响对应 Profile。同批其他 Profile 继续运行，批次结束后仍按现有规则关闭窗口。

## 11. 安全与清理

- 服务端只接收公开 `profile_token`，原始 AdsPower Profile ID 不进入 HTTP 响应。
- 只保存数值事件和版本元数据。
- 失败、取消、页面断开和服务关闭均执行窗口关闭、会话释放及 Profile 租约释放。
- 重新校准未发布前，上一已通过自动回放验收的版本继续有效；升级前版本仅保留记录，不再执行。
- 校准 Profile 不允许与任务、点选器或另一校准重入。

## 12. 验收标准

- 一个测试 Profile 能连续完成三次真实单格向下滚动校准。
- 三次都必须各切换一个视频，随后自动 Dry-Run 恰好切换一个视频，页面才显示新版本。
- Dry-Run 每个候选只发送一个 wheel 事件；正式执行也只发送一个已验证事件。
- 升级前未经过 Dry-Run 的版本不能继续供策略执行。
- 两个 Profile 同时执行时，各自只切换一个视频，无抖动、无跳过。
- 没有有效校准时，包含滚动动作的策略在打开 Profile 前明确失败。
- 重新校准失败或取消后，上一已通过自动回放验收的稳定版本仍能使用。
- 取消、失败和成功都会关闭校准窗口并释放租约。
- 一个 Profile 回放失败不会终止同批其他 Profile。
- 执行历史能显示使用的校准版本、事件数量和切换结果。

## 13. 测试范围

- 数据归一化：三样本一致、不同事件数量、20% 边界、方向不一致，并验证基础值来自最接近中位数的真实样本。
- Dry-Run：固定倍率顺序、单事件调用、首次单切换即停止、零切换继续、跨多视频停止、失败后稳定性检查。
- 存储：`replay_validated` 迁移、旧版本不可执行、原子发布、失败回滚。
- 服务：租约冲突、启动、轮询、自动完成、取消和清理。
- HTTP：请求字段白名单、公开错误、敏感信息脱敏。
- UI：按钮互斥、三步状态、Dry-Run 候选状态、轮询停止、失败信息及旧版本展示。
- 执行器：缺少已回放验证版本的预检、单事件回放、视频切换验证、失败不补发、批次隔离。
- 集成验收：一个 Profile 完成人工采样与自动 Dry-Run；两个 Profile 并行各切换一个视频。
