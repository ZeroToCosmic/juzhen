# Task 9 Production Repair Design

Date: 2026-07-27

## Goal

Repair the production paths exposed by the first Task 9 live run:

1. mask AdsPower Profile IDs at every public browser response and log boundary;
2. make TikTok wheel-driven video switching wait for asynchronous feed snap and
   virtualization instead of issuing the next pulse immediately;
3. resolve the comment entry again after a verified video switch and after the
   new active article has rendered;
4. retain earlier successful action measurements when a later action fails;
5. rerun Task 9 only on the two explicitly authorized AdsPower profiles.

This design refines the previously approved verified-scroll and resilient-locator
designs. It does not change saved strategy shapes or persistence.

## Confirmed product decisions

- Public Profile IDs use the form `***` plus the final four characters, for
  example `***xcto`.
- Full Profile IDs remain available only inside the server where AdsPower calls,
  locks, leases, and request correlation require them.
- A configured scroll count remains the number of verified TikTok video
  switches. Existing numeric values are not converted.
- Every wheel pulse remains exactly `-120` for upward scrolling or `+120` for
  downward scrolling.
- A comment-entry click is dispatched at most once. Only pre-dispatch locator
  resolution may wait and retry.
- The authorized live-test scope is limited to the profiles represented publicly
  as `***xcto` and `***xctm`.
- The Task 9 rerun must not post a comment.

## Considered approaches

### A. State-aware wheel pulses

After each wheel pulse, observe the feed for a bounded period and accept success
only after a different center article is stable. This preserves real wheel
events and verified-count semantics.

This is the selected approach.

### B. Direct DOM scrolling

Calling `scrollIntoView()` or assigning `scrollTop` would be simpler, but it
would no longer test or execute the requested mouse-wheel behavior.

### C. Larger or rapid wheel bursts

Increasing the wheel delta or sending an unobserved burst may move the feed more
often, but it can skip videos and cannot prove that one configured count equals
one successful switch.

## Public Profile ID boundary

### Masking rule

For any non-empty Profile ID:

- if it is already in the exact public form `***xxxx`, preserve it;
- otherwise return `***` plus its final four Unicode characters;
- values shorter than four characters are fully masked after `***` without
  exposing their content.

The masking helper is applied by key at the recursive public-data boundary when
the normalized key is `profileid`. It is also used by the explicit public
strategy/session projectors so values cannot bypass masking by being assembled
before or after the generic sanitizer.

### In scope

- browser start, navigate, execute, record, and stop responses;
- nested `results`, `sessions`, recovery records, and batch results;
- `browser_operations.jsonl`;
- staged browser errors that include a structured Profile ID field;
- browser-operation result tables that render those public responses.

### Out of scope

Internal AdsPower requests, session maps, locks, leases, saved account
configuration, and form request values keep the full ID because they are
operational identifiers rather than public diagnostics.

Error strings must not interpolate a full Profile ID. Structured fields are
preferred; any legacy message generated by this repair must use the masked
value.

## TikTok switch state machine

### Existing defect

The current post-pulse observer returns `None` as soon as its first sample still
matches the pre-pulse video. TikTok often applies wheel scrolling, snap
animation, and virtual-list replacement asynchronously. The runtime therefore
emits the next pulse before the current pulse has had time to settle.

### One verified switch

1. Capture the current center video identity and visible feed-container geometry.
2. Move the synthetic pointer to the center of that container.
3. Emit one wheel event with delta `+120` or `-120`.
4. Observe until the current pulse's observation deadline:
   - an unchanged first sample is not failure;
   - continue polling while the old video remains centered;
   - when a new identity appears, require the same new identity in two
     consecutive samples and require stable container scroll position;
   - if the candidate changes again, restart stability sampling;
   - if no stable new identity appears, return control for the next pulse.
5. Increment `completed_switches` exactly once only after a stable different
   identity is accepted.

The accepted new state becomes the baseline for the next requested switch.

### Bounds

- Per-pulse observation window: 450 milliseconds.
- Per-switch total deadline: 8 seconds.
- Per-switch pulse count:

  ```text
  min(24, max(4, ceil(container_height / 120) + 4))
  ```

- The earlier of the pulse bound or total deadline terminates an unverified
  switch.
- Configured random interval is still applied only between completed switches.
- Successfully dispatched wheel events are counted even when no switch follows.
- A timed-out or ignored pulse never increases `completed_switches`.

The implementation must crop every capture, mouse call, poll sleep, and
observation wait to the remaining deadline. It must not leave background tasks.

### Identity and privacy

Identity remains based on video ID, stable article ID, or the existing
deterministic fallback. Only twelve-character hashes may appear in public
switch records. Captions, usernames, full URLs, selectors, and page content are
not diagnostics.

## Comment-entry readiness after switching

### Existing defect

The comment entry resolved before the first live run, but after a verified
switch TikTok replaced the active article and the immediate resolver found no
actionable candidate. The click was never dispatched.

### Pre-dispatch resolution

For a recognized comment-entry action:

1. resolve the current `active_video` scope from the current page;
2. attempt the alias's ordered locator candidates;
3. when resolution fails only with a safe transient state, wait and try again
   against a freshly resolved active-video scope;
4. stop when one actionable candidate resolves or after three seconds.

Safe transient states are limited to:

- `element_candidate_not_found`;
- active-video scope temporarily unavailable during virtual-list hydration;
- candidate present but temporarily not visible/actionable.

Ambiguous candidates, invalid definitions, missing aliases, invalid scopes, and
page-closure errors fail immediately or follow the existing one-time
page-lifecycle recovery.

Every attempt re-resolves the scope and locator. No element handle is carried
across attempts.

### Dispatch boundary

Once mouse movement or clicking begins, locator-readiness retry ends. The
runtime sends exactly one click and retains the existing comment-panel
postcondition observation. A missing postcondition never triggers another
click.

Comment input and submit actions continue to resolve independently inside the
visible comment panel.

## Partial action evidence

When action N fails, the staged execution error carries a sanitized copy of
actions 1 through N-1. The public failure projection exposes these completed
actions alongside the failing action metadata.

This ensures a successful prerequisite scroll remains measurable if the
following comment-entry resolution fails. The copied actions use the existing
safe action projector and cannot include input text, selectors, raw video
identities, or full Profile IDs.

## Persistence and compatibility

- No config schema version changes.
- No migration of saved scroll counts.
- No change to saved locator definitions, strategies, patterns, accounts, or
  Cookie settings.
- Refresh and launcher restart continue to read the existing persisted data.
- Normal config backups remain untouched.

## Test-driven implementation

Tests are written to fail before each production change.

### Profile masking

- top-level and nested `profile_id` values become `***xxxx`;
- already masked values remain stable;
- short identifiers reveal no original characters;
- execute/start/navigate/stop responses and browser logs contain no full test
  IDs;
- internal controller calls still receive the full ID.

### Video switching

- an unchanged first post-pulse sample is polled again;
- an asynchronously appearing new identity is accepted only after two stable
  samples;
- an unchanged pulse waits for its observation window before another pulse;
- multiple pulses can produce exactly one verified switch;
- pulse and total deadlines are enforced;
- up/down deltas remain exactly `-120`/`+120`;
- ignored pulses affect `wheel_events`, not `completed_switches`;
- existing page-replacement recovery remains bounded and non-duplicating.

### Comment readiness

- comment entry can appear after one or more transient lookup failures;
- every attempt re-resolves active-video scope;
- ambiguity and invalid configuration are not retried;
- locator timeout sends zero clicks;
- successful readiness sends exactly one click;
- postcondition timeout never repeats the click;
- input and submit still resolve in the visible panel.

### Partial evidence

- a later failure retains earlier successful scroll measurements;
- unsafe result fields remain excluded;
- switch identities remain hashed.

All existing Python and JavaScript tests must still pass.

## Task 9 rerun

After automated verification:

1. confirm the active configuration signature before the run;
2. start and tile only `***xcto` and `***xctm`;
3. run the read-only locator draft check;
4. run one downward `[3, 3]` verified-switch action per profile;
5. run upward only when the profile has a valid non-initial precondition;
6. test comment-entry readiness only after a verified switch;
7. do not input or submit comment content;
8. verify persistence across refresh and launcher restart without altering
   unrelated configuration;
9. stop both profiles once and confirm they are inactive;
10. verify the public report and browser log contain no full Profile IDs.

The rerun report records pass, fail, or blocked outcomes with actual completed
switches, wheel events, safe switch hashes, locator diagnostics, and cleanup
evidence. It must not claim success from wheel dispatch alone.

## Success criteria

- No public browser response or new browser log line contains either authorized
  full Profile ID.
- Each completed scroll count corresponds to a stable center-video identity
  change.
- Both directions preserve exact wheel delta and bounded execution.
- A comment-entry action after switching gets a bounded fresh-resolution window
  and sends at most one click.
- A later action failure retains previous successful action measurements.
- Full automated suites pass.
- Task 9 is rerun only within the authorized two-profile scope and cleanup is
  confirmed.
