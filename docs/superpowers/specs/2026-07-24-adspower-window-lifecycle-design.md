# AdsPower 窗口平铺与执行会话生命周期设计

日期：2026-07-24

## 目标

解决两个关联问题：

1. 打开 1–8 个 AdsPower 浏览器窗口后，在 Windows 主显示器可用区域内等面积排布，并在排布完成后将这些窗口带到前台一次。
2. 多窗口执行积木策略时，即使 TikTok 或 AdsPower 替换、关闭当前页面 Tab，后续动作也能重新绑定有效页面；单个窗口失败不得中断其他窗口。

## 已确认的现状与根因

- 现有 `window_tiler.py` 已能计算 1–8 个窗口布局；2 个窗口为左右各半，4 个窗口为四等分。
- 现有置前操作依赖 `HWND_TOP`、`BringWindowToTop` 和 `SetForegroundWindow`。Windows 可能拒绝直接设置前台窗口，当前实现不会重试，也未设置持续置顶。
- 用户选择的语义是“打开并平铺后置前一次”，不使用 `HWND_TOPMOST`，避免浏览器持续覆盖其他程序。
- 现有窗口发现会在标题不能匹配资料时退化为按枚举顺序选择窗口。存在其他 AdsPower 窗口时可能移动错误窗口。
- 真实日志显示策略第一个动作只是等待，但失败动作会在第 2、4、6 步之间变化，错误均为 `Target page, context or browser has been closed`。
- 现有执行器在连接后固定保存 `context.pages[0]`，整个策略期间不再检查页面生命周期。TikTok 或 AdsPower 替换、关闭该 Tab 后，后续动作仍使用旧 page。
- 导航准备和策略执行当前分别建立 Playwright 连接，页面选择与动作执行之间存在额外生命周期缝隙。

## 总体架构

每个 AdsPower 资料使用一条独立的 Playwright/CDP 执行会话。该会话在同一次连接中依序完成：

1. 等待 CDP 就绪。
2. 获取浏览器 context。
3. 清理无关旧 Tab。
4. 打开或切换到目标网址。
5. 执行完整积木策略。
6. 断开自动化连接，但不关闭用户拥有的 AdsPower 浏览器窗口。

多个资料继续通过线程池并行执行。窗口之间不共享 `browser`、`context`、`page`、Playwright 实例或动作状态。

## 页面选择与恢复

### 有效页面选择

会话维护“当前页面”，但每个动作开始前必须重新验证：

- browser 仍连接；
- context 仍存在；
- page 未关闭。

当前 page 失效时，从当前 context 的页面集合中重新选择。优先顺序：

1. 未关闭且 URL 不是 `about:blank` 的页面；
2. URL 与目标网址域名相同的页面；
3. 当前可见页面；
4. 最新创建的有效页面。

没有有效页面时，短时间轮询等待新 Tab；超时后返回结构化错误，不无限等待。

### 动作期间失效

- `move`、`scroll_up`、`scroll_down`、`pause` 属于可安全恢复动作。若执行期间 page 关闭，重新绑定页面后最多重试一次。
- `click`、`keyboard_input` 不自动重试。系统无法可靠判断关闭前动作是否已产生副作用，盲目重试可能造成重复点击、重复输入或重复提交。
- browser 或 context 已关闭时，停止当前资料的策略并返回失败；其他资料继续执行。
- 恢复只针对同一个 AdsPower 资料的 context，不允许跨资料借用页面。

### 日志

页面生命周期日志记录：

- profile ID；
- 策略 ID；
- 动作 ID、动作序号和动作类型；
- 旧页面 URL；
- 关闭类型：page closed、context closed 或 browser disconnected；
- 是否发现替代页面；
- 替代页面 URL；
- 是否发生安全重试及结果。

日志不得输出 CDP 地址、API Key、Cookie 或页面敏感内容。

## 窗口识别

每个已就绪资料的 CDP 地址包含本机调试端口。窗口映射流程：

1. 从 CDP 地址解析本地端口。
2. 根据监听端口定位 SunBrowser/Chromium 浏览器进程。
3. 根据进程及其父子进程树定位顶层可见窗口句柄。
4. 将窗口句柄与 profile ID 建立一对一映射。

若不能获得精确映射：

- 候选窗口唯一时允许使用该候选；
- 候选窗口不唯一时返回“窗口映射失败”；
- 不得按不确定枚举顺序移动窗口。

## 窗口布局与置前

- 使用 Windows 主显示器工作区，自动排除任务栏。
- 平铺前恢复最小化窗口。
- 1 个窗口占满工作区。
- 2 个窗口按一行两列排列，左右各占 50%。
- 4 个窗口按两行两列排列，每个占 25%。
- 3、5–8 个窗口使用现有等面积布局算法，保证覆盖工作区、互不重叠。
- 设置位置和尺寸后读取实际窗口矩形，验证未越界、未重叠且与目标矩形一致。
- 所有窗口完成布局后依次带到前台一次。
- 不设置持续置顶。
- `SetForegroundWindow` 被 Windows 拒绝时，使用临时线程输入附加方式重试；重试后立即解除附加。
- 仍无法置前时记录明确失败，不伪报成功。位置和尺寸已成功时仍保留平铺结果。

## 执行流程

单个资料的执行阶段：

1. `session_check`：取得或启动 AdsPower 会话。
2. `window_map`：建立 profile 与窗口句柄映射。
3. `tile`：恢复、缩放、定位并验证窗口。
4. `foreground`：将已平铺窗口带到前台一次。
5. `connect`：建立该资料独立 Playwright/CDP 连接。
6. `prepare_page`：选择页面、清理旧 Tab、打开目标网址。
7. `execute_actions`：执行策略并在动作边界验证 page。
8. `disconnect`：只断开自动化连接。

页面准备和策略执行必须复用步骤 5 创建的同一连接。

## 并发与错误隔离

- 每个资料继续由独立工作线程处理。
- 每个线程拥有独立事件循环和 Playwright 实例。
- 一个资料的页面、窗口映射、导航或动作失败只影响该资料。
- 会话租约覆盖从 AdsPower 会话取得到策略执行结束的完整区间。
- 普通“测试执行策略”完成后不关闭 AdsPower 窗口。
- 原有批量任务若明确要求批次结束后关闭窗口，继续通过现有租约关闭机制执行。

## 兼容范围

保持不变：

- 策略、元素、录制模式及持久化格式；
- Ghost Cursor 轨迹；
- 滚轮最小/最大次数随机语义；
- 每个滚轮次数对应一个 `page.mouse.wheel()` 事件；
- 数据统计及其他业务模块；
- 最多 8 个并行平铺窗口的现有限制。

## 自动测试

### 窗口测试

1. 1–8 个窗口均生成合法、不重叠、覆盖工作区的布局。
2. 2 个窗口精确左右等分。
3. 4 个窗口精确四等分。
4. 任务栏工作区偏移正确。
5. 最小化窗口先恢复再定位。
6. CDP 端口能映射到正确进程树和窗口句柄。
7. 多个候选无法确认时失败，不移动任意窗口。
8. 设置后实际矩形验证通过。
9. 前台设置首次失败时执行一次安全重试。
10. 不调用 `HWND_TOPMOST`。

### 页面生命周期测试

1. 等待动作完成后旧 page 关闭，新 Tab 出现；滚动动作自动切换新 Tab。
2. 滚动中 page 关闭；重新绑定后只重试一次。
3. 点击期间 page 关闭；不自动重试。
4. 键盘输入期间 page 关闭；不自动重试。
5. context 关闭；当前资料失败并包含明确阶段。
6. browser 断开；当前资料失败并包含明确阶段。
7. 两个资料并行执行，一个页面失效不影响另一个。
8. 导航和动作使用同一 Playwright 连接。
9. 执行结束只停止 Playwright 连接，不调用浏览器关闭。
10. 生命周期日志经过敏感信息脱敏。

## 实机验收

用户在界面选择两个可测试 AdsPower 资料，执行包含“等待 → 向下滚动”的策略：

1. 两个窗口位于主屏左右两半。
2. 两个窗口在平铺后被带到前台一次。
3. 切换到其他程序后，浏览器不会持续置顶。
4. 两个窗口独立执行准确数量的滚轮事件。
5. 页面发生 Tab 替换时，安全动作继续执行。
6. 任一窗口失败时，另一窗口继续执行。
7. 策略结束后两个 AdsPower 窗口保持打开。

## 非目标

- 不实现持续置顶。
- 不跨多个显示器铺满桌面。
- 不使用 AdsPower Synchronizer 同步用户输入。
- 不对点击和键盘输入执行不确定的自动重试。
- 不修改策略保存结构或数据统计模块。
