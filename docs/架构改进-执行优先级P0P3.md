## P0 存储改造（补充决策）

### P0.1 日志/事件落点选择
- **结构化业务事件**（动作回执、进度、指标）：PG 按天分区表（`task_events_YYYYMMDD` 分区或 task_results 分区）——v1 用 PG 足够（写 ~40/s）
- **非结构化日志**（Agent 文本日志）：**Loki**（与 Grafana 监控栈一体，轻量，保留 30 天）
- **ClickHouse**：**v2 演进项**——当"动作事件分析/行为画像"需求出现时引入（结构化事件量大且需要 SQL 分析时）；v1 不引入（避免双 OLAP 栈）
- **决策**：v1 = PG 分区（事件）+ Loki（日志）；ClickHouse 挂 v2 决策点

### P0.2 PG 按天分区
- 分区表：`task_results`、`audit_events`、`device_heartbeats`、`task_events`（新增）按月/按天分区
- 分区策略：按月分区 + 90 天归档任务（移到 `*_archive` 表或对象存储）
- 索引随分区局部化；写入只落当月分区

### P0.3 写缓冲
- **Redis 缓冲**（TTL 60s）：心跳、窗口计数、进度计数——定期批量回写 PG（每 5-10s 一批）
- 结果/状态迁移**不缓冲**（直接事务写，保证一致性与 Outbox 语义）
- 缓冲内容必须可容忍丢失（心跳/计数），状态类永不进缓冲

### P0 验证
- S3 断言：PG 写 ≤50/s 且分区裁剪生效（EXPLAIN）；Loki 日志检索 P95 <1s；缓冲丢失率 0（状态类）

## P1 调度改造（补充决策）

### P1.1 分片异步拆解
- 同前（#3/#4）：任务创建返回 202，后台拆解 job 按 1,000-5,000/片流式入库，进度字段可查

### P1.2 设备区间分片调度（Sharding）
- **分片键 = 设备**（subtask 的候选设备集合预计算自 Profile 权威设备/副本 → subtask 路由到其候选设备所属分片）
- central 多实例时：每个实例负责一段设备区间（`device_id` 哈希取模或区间表），**只调度/回收本片设备**——无跨实例争抢（替代对 SKIP LOCKED 的强依赖；SKIP LOCKED 保留为片内并发兜底）
- **实例管理**：分片注册表（`central_instances` 表 + 心跳）；设备增删时 rebalance（新设备落在最低负载片）
- 单实例模式：全设备一片（现有行为）
- **与 F12a 关系**：Sharding 是"静态路由"（零锁争抢），F12a 的 SKIP LOCKED/唯一约束是"片内兜底"——两者并存

### P1 验证
- S4：双实例扩展性（每实例只处理本片设备，无重复分配——唯一约束断言）；15 万拆解专项（同前）

## P2 前端降频（补充决策）

### P2.1 WS 1Hz 汇总推送协议
- 服务端聚合器：**每租户每秒最多 1 条汇总帧**
- 汇总帧格式：`{"type":"summary","seq":"...","payload":{"subtask_results":N,"dlq":N,"running_windows":N,"queued":N,"recent":[{"status":"SUCCESS","count":N}]}}`
- 事件帧（`subtask.result` 等原始事件）**不再逐条推**——只推 1Hz 汇总 + 低频里程碑（任务创建/账户状态变更这类需要即时反馈的，可放宽到 5Hz 或独立低速率通道）
- 前端：汇总帧驱动看板数字增量更新；原始事件由 REST 详情页按需获取

### P2.2 日志按需点播
- `GET /api/central/subtasks/{id}/logs?cursor=&limit=`（REST 分页）
- Agent 动作日志保留本地 JSONL + 按需同步（central 索引摘要：task/subtask/时间/级别，正文按需拉取或 Loki 检索）
- WS 不再承担日志流

### P2 验证
- S3：WS 出口 ≤1 条/s/租户；前端 30 分钟内存稳定；日志点播 P95 <500ms

## P3 端侧瘦身（补充决策）

### P3.1 Cache 自动清理
- 每日低峰（可配置时窗）批量清理超阈值 Profile 缓存（阈值 200MB，活跃窗口跳过）
- 清理前记录：Profile 目录大小 → 清理后大小（审计日志）

### P3.2 磁盘水位
- 心跳上报 `disk_free_gb`；水位告警（<50GB 警告 / <20GB 停新任务）
- max_accounts 按磁盘动态计算（M1 字段就位，M3 系数校准）

### P3.3 AdsPower 迟钝治理（补入 P3，与 Cache 同域）
- 看门狗强杀 = 连续 N 次超时 + 持续窗口（防误杀）
- 动态背压：API 响应均值超阈值 → 降窗口并发（3→2→1）
- 单台容量实测（S2）→ max_accounts 系数

### P3 验证
- S2 实测：150 Profile/台磁盘占用 + AdsPower P95 响应；清理任务生效；慢 API 模拟不误杀
